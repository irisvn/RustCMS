Database schema ​

The framework's migrations create the tables below. Use this page when you write reports or support queries, plan a backup, or check what a table holds before you touch it. Your own tables live next to them in the same database.

rustcms migrate runs the framework's migrations before yours: an application's migrator starts from rustcms::migration::framework():

rs
pub struct Migrator;

impl MigratorTrait for Migrator {
    fn migrations() -> Vec<Box<dyn MigrationTrait>> {
        let mut migrations = rustcms::migration::framework();
        let app: Vec<Box<dyn MigrationTrait>> = vec![
            Box::new(m20261011_155203_create_posts_table::Migration),
            Box::new(m20261012_000001_create_categories_and_post_content::Migration),
            Box::new(m20261013_000001_add_deleted_at_to_posts::Migration),
            Box::new(m20261014_000001_add_media_to_posts::Migration),
            Box::new(m20261014_000002_add_color_to_categories::Migration),
            Box::new(m20261015_000001_add_attributes_to_posts::Migration),
            Box::new(m20261022_000001_create_tags::Migration),
            Box::new(m20261101_000001_create_integrations::Migration),
            // rustcms:migrations
        ];
        migrations.extend(app);
        migrations
    }
}

Column types are shown portably:

  • instant: TIMESTAMPTZ on PostgreSQL, DATETIME(6) in UTC on MySQL, text on SQLite;
  • bigint id: auto-increment BIGINT;
  • uuid: UUID on PostgreSQL, the database's UUID mapping elsewhere;
  • json: JSON (JSONB is not used).

Never write the access-control tables yourself: every change to roles, permissions and their assignments goes through RbacService (Roles & permissions), which checks the actor, locks, audits and invalidates the permission cache.

Users and access ​

text
                          ┌──────────────────────────┐
                          │ users                    │
                          │ id, email (unique), …    │
                          │ auth_version, is_active  │
                          └───────────┬──────────────┘
         (model_type = 'user', model_id = users.id as text)
              ┌───────────────────────┼──────────────────────────────┐
              ▼                       ▼                              ▼
┌──────────────────────────┐ ┌───────────────────────────┐ ┌───────────────────────────┐
│ model_has_roles          │ │ model_has_permissions     │ │ sessions / tokens / JWT   │
│ role_id, model_type,     │ │ permission_id, model_type,│ │ personal_access_tokens    │
│ model_id                 │ │ model_id   (direct grants)│ │ jwt_families → jwt_refresh│
└───────────┬──────────────┘ └─────────────┬─────────────┘ │ user_tokens (reset/invite)│
            ▼                              ▼               └───────────────────────────┘
┌──────────────────────────┐ ┌───────────────────────────┐
│ roles                    │ │ permissions               │
│ name + guard_name unique │ │ name + guard_name unique  │
│ is_system, is_privileged │ │ group, orphaned           │
└───────────┬──────────────┘ └─────────────▲─────────────┘
            └──────► role_has_permissions ─┘
                     (role_id, permission_id)

A user's permissions in a guard are those of their roles in that guard, plus their direct grants. Orphaned permissions are left out. super_admin passes every check of its guard.

role_has_permissions, model_has_roles, model_has_permissions ​

A copy of these tables gives nobody a working credential: only hashes are stored. Restoring a backup still requires ending every sign-in (backup and restore).

Reading them ​

For reports or support, read-only SQL is fine. For example, everyone holding a permission in the admin guard:

sql
SELECT DISTINCT u.id, u.email
FROM users u
JOIN model_has_roles mr ON mr.model_type = 'user' AND mr.model_id = CAST(u.id AS CHAR(20))
JOIN roles r ON r.id = mr.role_id AND r.guard_name = 'admin'
LEFT JOIN role_has_permissions rp ON rp.role_id = r.id
LEFT JOIN permissions p ON p.id = rp.permission_id AND p.orphaned = FALSE
WHERE p.name = 'posts.update' OR r.name = 'super_admin';

(Direct grants: the same through model_has_permissions. On PostgreSQL, use CAST(u.id AS TEXT).) Writes go through RbacService or the System pages.

rustcms_locks ​

ColumnTypeNotes
namevarchar(64)primary key

The migration inserts every row up front: rbac, and lineage:0 … lineage:1023 and idem:0 … idem:1023 (names are hashed into 1,024 slots). On MySQL, rustcms::db::xact_lock(txn, name) locks the row with FOR UPDATE until the transaction ends; a name without a row is an error, so on MySQL only these names work. PostgreSQL takes an advisory lock on a hash of the name and SQLite already holds its write lock: the table exists there only so every database has the same schema.

A job's row is deleted when it finishes; a failed job stays (with failed_at) until it is retried or forgotten, or until the workers delete it after queue.failed_retention_days (30 by default). Indexed on (queue, failed_at, available_at) for claiming.

job_receipts: key varchar(191) primary key, created_at (indexed). A job records a receipt in the transaction of its effect (rustcms::queue::once), so the effect applies once even when the job runs again, as long as the receipt is kept: receipts are deleted after queue.failed_retention_days (30 by default).

Your tables ​

Your migrations add tables next to these, in the same database. Keep your data in your own tables and reference users.id (bigint) when you need a user: framework migrations may change their tables in later releases, and the access-control and credential tables are written only through the framework (RbacService, the auth routes). Secrets in your tables use rustcms::crypto::Encrypted<T> in a Text column (Encrypted columns).
