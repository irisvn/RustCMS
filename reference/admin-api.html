Admin API ​

The admin panel talks to the server through a JSON API under <admin_path>/api (default /admin/api). You rarely call it yourself, but it is what resources expose, and its rules are the rules of every client: tests, scripts, a custom front end.

Every request uses the admin session (cookie) and, for writes, the CSRF token and an allowed Origin (Authentication). Responses, errors included, are Cache-Control: private, no-store; unknown paths under /api are JSON 404. Errors follow the standard format; values follow the wire format.

Options are available to users who may use the field. When a record-level policy hides more than 1,000 candidates before 50 visible ones are found, the endpoint answers 422 on search: refine the search. Edit and view forms send record=<key>: the record is loaded in the user's scope and the policy decides on it (update with a writable field, or view with a readable one), exactly as for the form and the update. Without record: read the field with view_any, or write it with create or update. Which records appear is decided by the target resource's scope and policy.

System routes ​

Users, roles and permissions of the admin guard, used by the System pages (Users, roles & account). Bodies are camelCase and refuse unknown fields. Every change goes through RbacService, which checks the permission again, locks, audits and refuses changes to accounts or roles the user may not manage (privileged roles, super admins, roles they hold). Writes that start from what the editor saw send it back (expected…): if it changed meanwhile the write is refused with 422 and the form issue stale, and nothing is saved.

Ids are strings. abilities tells the page which buttons to show; the server decides again on each request.
  • Roles: creating one needs every permission it grants; deleting one needs its active permissions; changing a role's permissions needs every permission added or removed; giving or taking a role needs that role's permissions. Nobody changes a role they hold.
  • After a change, a caller who may not read the user (no users.view, and not themselves) gets 204 instead of the record.
  • Creating a user and resetting a password hash a password: each has its own per-minute quota per acting user (creation: auth.attempts_per_ip; reset: auth.attempts_per_identifier), separate from the sign-in throttle (429 beyond). Invitations are limited to 20 a minute per user, resends to 5.
  • Only roles of the admin guard are listed and managed here; API-guard roles are managed with rustcms role:assign (Limitations).

Other routes under the same prefix ​

  • Authentication of the panel lives at <admin_path>/api/auth/…: csrf, login, logout, me, password, logout-others, locale, forgot-password, reset-password, invitation. See Authentication.
  • Your own JSON routes for panel pages are declared with AdminRoutes and live at <admin_path>/api/x/…, including streams (AdminRoutes::events) and sockets (AdminRoutes::socket). Nothing built in lives there. See Admin routes and Realtime.

Lists ​

page, per_page (≤ 100; the panel offers 10, 25, 50 and 100), sort (title or -title), search (case-insensitive as the database folds case: Unicode on PostgreSQL, ASCII on SQLite; % and _ are literal), and filters filter[<field>][<op>]=<value> with op in eq, in, gt, gte, lt, lte. Values are read by field type: filter[published][eq]=true, filter[category_id][in]=1,2. JSON clients use the strict wire format.

trashed=with|only lists trashed records too, or only them, on resources with soft deletes (table.softDeletes); elsewhere it is a 422. It needs the restore or force_delete ability (schema abilities.restore / abilities.forceDelete), otherwise 403, and a trashed record is listed only if the policy allows view and restore or force_delete on it.

Records ​

json
{
  "key": "0199d3a4-…",
  "title": "Hello",
  "abilities": { "delete": true, "update": true, "view": true },
  "data": { "title": "Hello", "author_id": "7", "price": "10.50", "category_id": 1 },
  "labels": { "category_id": "News" }
}
  • data holds readable fields only, and is empty (no title, no labels) when the user may not view the record, e.g. the result of an update-only write. One exception on a record the user may view: an encrypted field the user may only write is sent as its masked state (state, revision, never the key names of a map) so the form can replace it.
  • abilities also holds one entry per action ("publish": true), decided by the policy and the action's visible_when on that record.
  • labels holds titles of related records. A related record the user may not see is shown as #<key>.
  • trashed: true marks a record in the trash (soft deletes; absent otherwise). Its abilities are view, restore and force_delete only; an active record of a soft-delete resource has restore and force_delete false.

Retrying writes safely ​

Creates (POST …/records, and POST …/relations/{relation} on a record), POST …/actions/{action}, media uploads (POST /media), import uploads (POST …/imports) and background exports (POST …/exports) accept an Idempotency-Key header (1–128 of A-Z a-z 0-9 _ -, otherwise 422 on idempotency_key). The key is claimed in the write's transaction, so the write and its receipt commit together or not at all. Repeating the request with the same key, by the same user, within 24 hours:

  • same request (body compared canonically: key order does not matter) → the first result, not applied again: a create answers its record as the user may see it now (key only when no longer visible); an action answers the first run's outcome with "replayed": true; an upload, import or background export answers the same media item, import or export. Admission is checked again (403 if the user lost the ability). Action outcomes, first or replayed, list processed and denied keys only for records the user may view now, and drop message and open unless the user may still view every processed record;
  • different request → 422 on idempotency_key;
  • the first request still running → the retry waits (up to 5 s), then answers 409 write_conflict (nothing applied; retry later).

Keys are per user, resource and operation. At most 1,000 live keys per user (429 beyond). idempotency:prune deletes expired receipts (serve does it hourly). Updates and deletes take no key: repeating them converges.

Limits ​

ParameterDefault
per_pagecapped at 100
search100 characters
filters per request10
items in an in filter100
keys per action or lookup500

options per lookup50

  • Rows checked one by one. A list, an export or a dashboard count reads the matching rows in batches and checks each when the policy decides record by record (view_depends_on_record()), when the list includes trashed records (trashed=with|only), and, on SQLite, for dashboard counts over date ranges. Past 10,000 matching rows:

    • a list or an export at once answers 422 too_many_matches;
    • a dashboard widget answers 200 with {"kind": "too_many"};
    • a background export fails with the reason too_many_matches.

    Narrow the search or filters. Other lists and counts (a policy that decides once for every record, active records, row filtering done by scope()) are counted by the database, with no such limit.

  • After a write. A committed create or update answers with the record as the user may see it. If reading it back takes more than 2 seconds (or would pass the request deadline), the answer holds the record's key alone; the write is committed either way.
