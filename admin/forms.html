Forms ​

form() describes how a resource's create, edit and record pages lay out its fields: which input edits each field, in which sections, tabs or columns. It is presentation only. What a user may read or write is decided by the fields and checked on the server, whatever the form shows.

The demo application: the post form's tabs.

Quick start ​

rust
fn form() -> Form {
    Form::new().columns(2).schema(components![
        TextInput::make("title").placeholder("A catchy title"),
        SelectInput::make("category_id"),          // options from the `belongs_to` target
        Toggle::make("published"),
        DateTimePicker::make("published_at"),
        Textarea::make("body").column_span(2),
    ])
}

Each input names a field. The form is built per user and operation (create, edit, view): inputs for fields the user may not read or write are left out or disabled, and the server checks everything again.

Without form(), the panel builds one input per field that is not .guarded():

A form() with only a width (Form::new().width(FormWidth::Wide)) keeps the generated inputs at that width.

Full example ​

The demo's post form: three tabs, a two-column tab, media, rich text, the tags of a belongs-to-many relation and key/value attributes.

}

A widget name is vendor/name: each part 1 to 32 characters of a-z, 0-9 and -.

Options are validated ​

The static .options(…) of a SelectInput or a CheckboxList bound what a client may write to the field, on every write path: API create and update, creates through a relation, and CSV imports (a row out of the options fails with its code). The value's type is checked first, as for any field.

InputA client may writeOtherwise (422 code)
SelectInputone of the option valuesnot_option
CheckboxLista list of option values, each at most once; [] is a valueinvalid (not a list), not_option, given_twice
  • null is checked as for any field (required, or a column that is not nullable); it is never compared with the options.
  • Select values are compared in their canonical wire form, column-aware: "0012" and "12" are the same i64, "10.5" and "10.50" the same Decimal(10, 2), an instant with an offset the same instant in UTC, a UUID in any case the same UUID. Options are declared in any of these spellings; the schema shows them canonical. Wire types stay strict: 12 (a number) is not an i64 value. The value stored is the option matched: "10.505" on a Decimal(10, 2) rounds to the option "10.50", which is what is written. Checkbox list items are compared as JSON values.
  • An update that leaves the field out keeps the stored value, even one outside the options (stored before the check, or by a hook).
  • The guarantee covers values a client sends. Hooks (mutate_before_create, mutate_before_update), action handlers and pivot columns write what they decide; validate there, or with a database CHECK constraint, if they must stay within the options too. Action forms and BelongsToManySelect check their own options.
  • A belongs_to select is different: its value must be a record the user may see, checked on every write; static options on it are not used.

Declarations that cannot hold stop the application at boot: an option that is not a value of its column (12 for an i64 column), one that would be stored as another value or read back differently ("10.555" on a column of scale 2, "100000000.00" beyond a Decimal(10, 2)'s precision, 0.1 on an f32 column, a timestamp with a fraction finer than microseconds), a CheckboxList on a column that is not JSON, or a field in several inputs that do not offer the same options (another set, a select and a checkbox list, or an input without options). The same options in another order or with other labels are allowed. SecretInput and SecretMapInput take no options.

The LMS offers two statuses in its enrollment form:

rs
const STATUSES: [(&str, &str); 2] = [(enrollment::ACTIVE, "Active"), (enrollment::WITHDRAWN, "Withdrawn")];
rs
fn form() -> Form {
    Form::new().schema(components![
        SelectInput::make("course_id"),

        NumberInput::make("progress").help("Percent of the course done (0 to 100)"),

The panel refuses any other status from a client. The write hooks still check it through the service they call (see validating in a hook): the course's enroll action and the seeder write enrollments through that service, not through the form.

rs
/// Whether an enrollment of `learner_id` in `course_id` with `status` may be
/// written; `current` is the enrollment being changed, if any. The caller
/// holds the course's lock.
pub async fn check(
    txn: &DatabaseTransaction,
    course_id: i64,
    learner_id: i64,
    status: &str,
    current: Option<i64>,
) -> AppResult<Result<(), Refusal>> {
    if status != enrollment::ACTIVE && status != enrollment::WITHDRAWN {
        return Ok(Err(Refusal::UnknownStatus));
    }
    let Some(course) = course::Entity::find_by_id(course_id).one(txn).await? else {
        return Ok(Err(Refusal::NoCourse));
    };
    let mut others = enrollment::Entity::find().filter(enrollment::Column::CourseId.eq(course_id));
    if let Some(id) = current {
        others = others.filter(enrollment::Column::Id.ne(id));
    }
    // Already in: said before the seats, which would not help.
    if others.clone().filter(enrollment::Column::LearnerId.eq(learner_id)).count(txn).await? > 0 {
        return Ok(Err(Refusal::AlreadyEnrolled));
    }
    if status == enrollment::ACTIVE {
        let taken = others.filter(enrollment::Column::Status.eq(enrollment::ACTIVE)).count(txn).await?;
        if taken >= u64::try_from(course.capacity).unwrap_or(0) {
            return Ok(Err(Refusal::NoSeat));
        }
    }
    Ok(Ok(()))
}

Number bounds ​

.min(n) and .max(n) on a NumberInput bound what a client may write to the field, like a select's options: on every write path, must be at least {min} (min_value) or may not be greater than {max} (max_value). .step(n) sets the step of the input's arrows and keyboard; it is a hint, not checked.

rust
NumberInput::make("level").min(1).max(5),
NumberInput::make("price").min(0.5).step(0.01),
  • i32 and f64 columns get a native number input (step 1 for i32 without one). i64 and decimal columns keep a text input, so no digit is lost; their bounds are still checked by the server.
  • As with options, the bounds cover what a client sends: hooks and actions write what they decide.
  • Integers and decimals are compared exactly with the bound as written (0.1 is 0.1). A decimal is also checked as its column rounds it: with .max(4.995) on a decimal(10, 2) column, 4.995 is refused, since it would be stored as 5.00.
  • A bound is an f64: an i64 bound above 2^53 is the nearest f64.
  • On an f32 column a value is checked as the f32 it is stored as, against the bounds as f32s: with .max(0.1), the value read back (0.10000000149…) is accepted again. Bounds that round to 0 as an f32 (1e-50) refuse to boot.
  • Action forms have no bounds yet: check the value in the action's handler.
  • Number inputs of action forms take no bounds.

Layouts hold inputs and other layouts with .schema(components![…]). Form::columns(n) (default 1), and .columns(n) on a section, a grid or a tab, lay their children out in n columns; .column_span(n) on an input widens it. The LMS course form uses two columns with a wide summary:

rs

Tabs hold only Tabs, and a Tab only sits in Tabs; a tab's id comes from its label and must be unique among its siblings. Tabs the user cannot see anything in are left out. On a failed save the panel opens the first tab with an error and focuses its input.

An editor layout ​

For long content (a post, a page), lay the form out like an editor: the whole width, a main column and a narrow aside with the details. The demo's categories use it:

rs
fn form() -> Form {
    // An editor layout: the whole width, a main column and an aside.
    Form::new().width(FormWidth::Full).schema(components![
        Split::make()
            .main(components![
                TextInput::make("name"),
                TextInput::make("slug").prefix("/categories/"),
                // The category's posts, edited in its form: each row is a post
                // (the posts resource's rules, policy and hooks apply).
                Repeater::make("posts")
                    .relationship()
                    .schema(components![TextInput::make("title"), Toggle::make("published")])
                    .item_label("{title}")
                    .add_action_label("Add a post"),
            ])
            .aside(components![Section::make("Display").compact().collapsible(false).schema(components![
                // Edited by the demo's extension widget (resources/admin/js/demo/color.js).
                CustomInput::make("color", "demo/color").props(json!({"palette": [
                    {"value": "#dc2626", "label": "Red"},
                    {"value": "#16a34a", "label": "Green"},
                    {"value": "#2563eb", "label": "Blue"},
                    {"value": "#9333ea", "label": "Purple"},
                ]})),
            ])])
    ])
}

The demo application: the category form at 1440 px.

  • Form::width(FormWidth::Default | Wide | Full): how wide the record's page is (create, edit and view; settings pages too): about 56rem (the default), 72rem, or the whole page.
  • Split::make().main(…).aside(…): from the lg breakpoint (1024px) the aside is 20rem wide on the right and stays in view while the main column scrolls; narrower screens show one column, the aside after the main one (.aside_first_on_mobile() puts it first). One split at most, at the form's top level; both columns hold inputs and layouts (sections, grids, tabs). A column the user cannot see anything in is left out. The view page lays the record out the same way.
  • Section::make(…).collapsible(collapsed): the user folds and unfolds the section with its title (a button with aria-expanded), starting folded when collapsed is true. Its inputs stay in the form while folded, and it opens by itself when one of them has an error. Nothing is remembered.
  • Section::make(…).compact(): less padding and spacing, for the aside.
  • TextInput::make(…).prefix(text) and .suffix(text): fixed text inside the input's border (/posts/ before a slug, .html after it), shown as written, never part of the value, and read by screen readers with the input; the record's page shows the value with them. Text inputs only.

Misusing them (a split inside a section, two splits, a grid that folds, a prefix on a number input) stops the boot.

Showing inputs under conditions ​

.shown_when(condition) on an input or a layout shows it only while the condition holds on the form's values:

rust
SelectInput::make("link_type").options([("internal", "Internal"), ("external", "External")]),
TextInput::make("url").shown_when(when("link_type").eq("external")),
Toggle::make("on_sale"),
Section::make("Sale").shown_when(when("on_sale").is_true()).schema(components![
    NumberInput::make("discount").clear_when_hidden(),
]),
ConditionHolds when the input's value
when("x").eq(v), .ne(v)equals (differs from) v
when("x").is_in([a, b])is one of the values
when("x").filled()is set: not null, blank text, [] or {}
when("x").is_true()is true (a boolean)
Condition::all([…]), Condition::any([…])every / one of the conditions hold
  • Live in the browser. The panel re-evaluates conditions on every change (each keystroke, selection or toggle), without a request: the inputs a condition reads need no extra declaration. A hidden input keeps what the user typed until the form is saved, so showing it again brings it back.
  • The server decides. On every write it evaluates the conditions again, on what the user's form holds (the record's values the user may read, or the declared defaults on create) with the request over it. A value sent for a hidden input is never stored; a hidden field keeps its stored value. With .clear_when_hidden(), a field that a write hides takes its column's default, else null, else an empty text or list.
  • Required when shown. A .required() field under a condition is only required while it is shown: when it is sent empty, on create, or when the write shows it.
  • A layout's condition applies to everything in it; a hidden input counts as empty for the conditions of other inputs. A field shown by another input without a condition is always shown.
  • Conditions compare values; logic that needs the database belongs in hooks.
  • Condition only on fields every user of the form may read. For a user who may not read a field (or view the record), the panel and the server treat it as empty, so the inputs it shows stay hidden for that user; nothing about its value can be learned from what is saved.
  • On a form opened from a relation, the key the relation sets is read by the conditions with the parent's key.

The same works on settings pages and in action forms (ActionField::shown_when; a hidden field reaches the handler as null).

Leaving with unsaved changes ​

A create or edit form with changes not saved asks before the user leaves it: the panel's dialog (Keep editing or Discard changes) for links and the browser's Back button, the browser's own prompt for closing or reloading the tab. It does not ask after a save, while a save is in flight or its outcome is unknown (the resource is paused and the retry is offered on any page), or when the session sends the tab elsewhere (sign-out, another user signing in).

Key-value ​

KeyValue edits a JSON column holding an object of text values ({"size": "M"}). The field is a key/value field when it declares .key_value() or .max_items(n), or a KeyValue input uses it; its bounds then apply to every write, API and hooks included, whatever the form shows: max_items pairs (default 50), keys up to 255 characters, values up to max_length (default 1,000). A stored value that is not an object of text is shown read-only and never rewritten; a nullable field can be cleared to "not set" (distinct from an empty object). The column must be JSON.

rust
Field::column(post::Column::Attributes).key_value().max_items(20).max_length(200),
// in the form
KeyValue::make("attributes").help("Extra details shown with the post, e.g. reading_time = 5 min"),

Repeaters ​

A Repeater edits a list of rows, each row several inputs, as Filament's does. Its value is a JSON array of objects in the column of its name ([{"question": "…", "answer": "…"}]); the column must be JSON.

rust
Repeater::make("faq")
    .schema(components![
        TextInput::make("question").required().max_length(200),
        Textarea::make("answer").required(),
        SelectInput::make("kind").options([("text", "Text"), ("link", "Link")]),
        TextInput::make("url").shown_when(when("kind").eq("link")),
    ])
    .min_items(1)
    .max_items(20)
    .reorderable()
    .collapsible()
    .item_label("{question}")
    .add_action_label("Add a question")
    .cloneable()
  • A row's rules are on its inputs. A row is part of one column, with no field of its own, so its inputs say what they need: .required(), .max_length(n) on text, .integer(), .min(n), .max(n) on numbers, options on selects (rows have no relationships). Elsewhere these rules come from the field, and the boot refuses them on inputs.
  • Values in a row: text for TextInput and Textarea, a JSON number for NumberInput, true/false for Toggle and Checkbox, the option's value for SelectInput, a list for CheckboxList, YYYY-MM-DD for DatePicker, an RFC 3339 instant for DateTimePicker, an object of text for KeyValue, any JSON for CustomInput, and a list for a nested Repeater (three deep at most). Empty inputs are left out of the row.
  • Each row is checked on the server, like a form: a key the row does not declare is refused, then each input's rules, then min_items and max_items. Errors name the row and the input: faq.2.question (faq.2.links.0.url nested, faq for the list); the panel shows them in their row.
  • Conditions (shown_when) in a row name inputs of the same row. An input hidden by its condition is removed from the stored row, and required means "required when shown".
  • Options: min_items, max_items, reorderable (buttons, or drag the handle), collapsible / collapsed, item_label("{input}") (each row's heading, a template as record titles), add_action_label, addable(false), deletable(false), default_items(n) (rows a create form starts with), cloneable.
  • Not in rows (yet): FileUpload and RichEditor (their media escape the reference checks), secrets, belongs-to-many inputs, tabs and splits.

On view pages the rows are shown read-only; an infolist shows them with a RepeatableEntry. Settings pages take repeaters too.

Child records ​

With .relationship(), the rows are the child records of the has-many relation named like the repeater, edited in the parent's form (the lines of an order, the answers of a question):

rust
// The parent (orders):
fn relations() -> Vec<Relation> {
    vec![Relation::has_many("lines", "order_lines", "order_id")]
}

Repeater::make("lines")
    .relationship()
    .order_column("position")
    .schema(components![TextInput::make("product"), NumberInput::make("quantity")])

// The child (order_lines) locks its parent: every write of a line locks its order first.
ResourceMeta::new("Line").lock_parent("order_id", "orders")
  • The child locks its parent (lock_parent through this relation; required): saves of an order and of its lines never interleave.
  • Row inputs are the child's fields, with the child's rules: its field rules, validation, options and bounds (declared on the child's form, shown in the rows), scope(), policy and hooks apply to every row, as when the row is written from the relation section. The child's key to the parent and the order column are set by the server, never inputs.
  • Not in rows: belongs_to selects, media, rich text, encrypted and belongs-to-many fields (edit them on the child's page). Hooks of the child should not write other resources; a hook adding media to a row is a server error (media are locked after every other record of a write).
  • One repeater per child resource in a form; a resource with relationship repeaters cannot link media records (belongs-to-many), and cannot lock a parent of its own (lock_parent has no chains).
  • Concurrent saves of one parent and its children wait for each other; a rare conflict through other records answers 409 ("try again"), nothing saved.
  • A save sends a change, not the list: the rows added, the fields changed in each row, the rows removed, and the order. Rows the user did not touch, rows another user added meanwhile, and rows the user cannot see are never written or removed.
  • One write: the parent row, then its rows (removed, changed, added, reordered), then the parent's after_save, which sees every row. A refusal anywhere (a row's validation, a child's policy or hook) rolls back the parent and every row.
  • Permissions: adding rows needs create on the child, changing them update, removing them delete (each row's policy decides too); the form offers only what the user may do.
  • Removing a row of a child with soft deletes moves it to the trash.
  • order_column(field) (an integer field of the child) keeps the rows in the user's order: they take the positions the visible rows held; rows the user cannot see keep theirs. A unique (parent, position) is fine. Moving a stored row needs update on it; without an order column the rows cannot be reordered.
  • min_items / max_items are checked by the server on the parent's rows when a save removes or adds rows, and min_items on the rows a new parent creates (a create without the repeater has none). Writes to the child elsewhere (its own page, the API) are not bounded by them.
  • addable(false) / deletable(false) are enforced by the server too.
  • New rows on an edit page show the child's create form inputs.
  • Rows edit their inputs only: a value for another field of the child is refused (lines.8.status: "is not allowed"), even one its own form writes.
  • Errors name the row by key or, for a new row, its reference: lines.8.quantity, lines.n1.quantity.
  • History: the parent's history shows "Rows changed" (how many rows were added, changed, removed, and whether they moved); each row has its own entries in the child's history.
  • The form edits up to max_items rows (at most 100); with more, the repeater is read-only and the relation section edits them. A save reorders at most 1,000 rows of one parent. View pages show the rows in the relation section, not in the form.
  • Not yet: conditions in relationship rows, repeaters inside them, and conditions on the repeater itself.

The demo's categories edit their posts this way (each row is a post):

Repeaters in lists, history and CSV ​

  • A count column shows the number of rows: TextColumn::make("faq").count() for a JSON repeater, TextColumn::make("lines_count").counts("lines") for a relationship.
  • The history shows a JSON repeater's change by row and input (faq › 2 › question), rows matched by position.
  • CSV exports write a JSON repeater as its JSON text; imports read that text and check each row as a save does (errors at faq.0.question).

Encrypted fields ​

The demo's integrations keep an API token and environment variables encrypted:

rs
fn fields() -> Vec<Field> {
    vec![
        Field::column(integration::Column::Name).required().searchable().sortable().max_length(60),
        Field::column(integration::Column::ApiToken).encrypted().label("API token"),
        Field::column(integration::Column::Env).encrypted_map().max_items(20).label("Environment"),
    ]
}

Both hold secrets sealed with APP_KEY in a text column without a default; the model's field is an Encrypted<T>:

  • encrypted() takes an Encrypted<String>;
  • encrypted_map() takes an Encrypted<BTreeMap<String, String>>.

The panel never shows them:

  • A secret string (SecretInput) shows Set, Not set or Cannot be read, with Replace and Clear. Leaving it alone keeps it.

  • Named secrets (SecretMapInput):

    • the names are listed, and each one is kept, replaced or removed;
    • new rows take a name and a value;
    • values are never shown or prefilled.

  • What the API returns and takes (for scripts and tests):

    Record valueWrite
    string{"state": "set"} (unset, unreadable){"replace": "…"}, {"clear": true}; left out: kept
    map{"state", "keys", "revision"}{"revision", "set": {…}, "keep": ["NAME"]}, {"revision", "clear": true}

  • Map rules:

    • Names neither kept nor set are removed.
    • On an existing record every change needs the revision it was read with. If someone changed the map meanwhile the save gets 409: reload and try again.
    • Keeping a name of a map that cannot be read (another APP_KEY) is refused; replacing every value recovers it.
    • A nullable map can be cleared back to not set (Clear in the form).
    • After a 409 the form offers Reload.
    • The key/value bounds hold on the result.

  • Who sees what: users who may read the field see the names. Users who may only write it see the state and can still replace everything.

  • Never allowed: encrypted fields are always write-only, never sortable, searchable, filterable, a title, a key, a relationship, media, rich text, part of a unique constraint, a table column, a pivot field or a dashboard column. They are never exported or imported, and always redacted in the audit log. SecretInput and SecretMapInput edit only encrypted fields, and those fields take no other input. Anything else stops the boot.

  • In hooks and actions: read the stored value with model.env.open(ctx.keyring()?, &context), and write it with Encrypted::seal. rustcms key:reencrypt re-seals them after a key rotation (rotating the key).

Checked at boot ​

Besides the layout and encrypted-field rules above, the boot stops when:

  • an input names something that is not a field;
  • a BelongsToManySelect does not name a belongs-to-many relation, shares its name with a field, appears twice, has options or a widget, targets the media library, or its relation has .required() pivot fields;
  • a CustomInput has an invalid widget name, or props over 4 KiB;
  • a key/value field is not a JSON column;
  • min, max or step is on an input that is not a NumberInput, or on a column that does not hold numbers; min is above max; the step is not positive; or two inputs of one field have different bounds;
  • a repeater's row is empty, holds tabs, splits, media, rich text, secrets or belongs-to-many inputs, or a select without options; a row input repeats a name; repeaters nest deeper than three; item_label names no input of the row; min_items or default_items is above max_items; the column is not JSON; required, max_length or integer is on an input outside a JSON row; repeater options are on an input that is not a repeater;
  • a condition names something that is not an input of the form, or an encrypted field; is_true is on a field that is not a boolean; eq, ne or is_in is on a JSON, rich text, media, date-time or key/value field, or compares with a value that is not of the field's kind; conditions depend on each other in a cycle; a BelongsToManySelect or an encrypted field has a condition; a relationship field has clear_when_hidden;
  • an input under a condition has a column that is not nullable and has no default (a record created while it is hidden could not be stored: declare a default or make the column nullable); clear_when_hidden is on an input without a condition, or on a non-nullable number, date or boolean column without a declared default.

Settings pages follow the same layout rules.
