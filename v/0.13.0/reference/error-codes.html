Error codes ​

Every standard application error the framework answers has a stable code, and every validation message has one too. Use this page when you write a client, translate the panel's messages or match errors in tests. The response shape is described in Errors.

Validation codes ​

A 422 response lists each message in errors / formErrors (English) and, in the same order, its code and parameters in issues / formIssues:

json
{
  "message": "The given data was invalid.",
  "code": "validation_failed",
  "errors": { "title": ["may not be longer than 200 characters"] },
  "issues": { "title": [{ "code": "max_length", "params": { "max": "200" } }] }
}

Clients translate by code and fall back to the message; parameters are text. A message that follows none of the templates below (one written by your own code) has the code custom (rustcms::i18n::CUSTOM) and params.message holds it. Every body has message and code; a 409 adds reason, a 422 adds errors, formErrors, issues and formIssues.

  • 409 means nothing was saved: reload, or send the request again (the panel offers to). Match on code and reason, not on the message.
  • 429 carries a Retry-After header: the advised delay, in seconds, before trying again (not always the exact time a limit resets).
  • 500 never includes the error itself: the server logs it, with the request id.
  • 503 unavailable answers a realtime stream or socket request while the server is shutting down. Connect again (to another instance).
  • import_row_written and import_stopped are 409 conflicts used inside the import job; they never reach a client (the import's report and status say what happened).
