On this page

Configuration ​

Configuration is read once, when a command starts, from config/*.toml, .env and the environment. Values that need a deploy to change go here; values admins change at run time go in settings.

Quick start ​

A new application has config/app.toml, auth.toml, http.toml and log.toml, and a .env. Change a value in the file, or override it from the environment:

toml
# Maximum request body (bytes) and timeout (seconds).
body_limit = 2097152
timeout_secs = 30
sh
export RUSTCMS_HTTP__BODY_LIMIT=2097152
rustcms serve
# or for one command: RUSTCMS_HTTP__BODY_LIMIT=2097152 rustcms serve

Sources and precedence ​

Sources, last one wins:

  1. built-in defaults,
  2. config/<section>.toml: each file becomes the section named after it (config/http.toml is [http]); a missing file keeps the defaults,
  3. well-known variables: APP_NAME, APP_ENV, APP_DEBUG, APP_URL, APP_KEY, APP_PREVIOUS_KEYS, DATABASE_URL, REDIS_URL,
  4. RUSTCMS_<SECTION>__<KEY>, e.g. RUSTCMS_HTTP__BODY_LIMIT=2097152.

.env is loaded first and never overrides variables already set in the environment. config/ is read from the working directory; .env is looked for in the working directory, then in its parents.

[mail] (config/mail.toml, feature mail) ​

Driver (disabled, smtp, log, memory), where the SMTP server comes from (settings or config), the hosts and ports mail may go to, timeouts and the rate: see Mail.

[queue] (config/queue.toml) ​

Workers and job leases: see Queues. serve runs queue.workers workers (2) when queue.enabled (left out: true, or false in API mode).

[redis] (config/redis.toml, feature redis) ​

KeyDefault

The environment ​

app.env (APP_ENV) names where the application runs: local, testing or production (the default, so a server that forgets it gets the safe behaviour). The framework uses it in a few places:

Behaviourlocaltestingproduction
migrate:fresh, migrate:refresh, db:seedrunrunrefuse without --force
mail.log_body (mail bodies, reset links, in the log)allowedrefused at startrefused at start
mail.allowed_hosts when admins set the SMTP server (smtp driver)optionaloptionalrequired
Page and mail templates re-read from disk on each renderin debug builds (cargo run)nono

Your code reads it as state.config().app.env, an Environment (rustcms::config::Environment::{Local, Testing, Production}), e.g. a seeder that refuses to create demo users in production.

app.debug (APP_DEBUG, true in a new .env) is loaded for your code as config.app.debug. The framework does not change its behaviour on it: error responses never contain internal details, whatever its value, and log verbosity comes from log.filter. Keep it false in production anyway, in case your own code uses it.

Your own sections ​

Any config/<name>.toml becomes a section your code reads with Config::section. Pick a name the framework does not use (above):

rust
#[derive(serde::Deserialize)]
struct Billing { currency: String }

// in a provider's register: config/billing.toml or RUSTCMS_BILLING__CURRENCY
let billing: Billing = app.config().section("billing").expect("[billing] settings");

section deserializes with serde: give fields #[serde(default)] to make them optional. The configuration is available as app.config() while the application is assembled and as state.config() afterwards.

Environment variables ​

Every key can be set from the environment as RUSTCMS_<SECTION>__<KEY> (nested keys with more __): RUSTCMS_APP__LISTEN=0.0.0.0:8000, RUSTCMS_AUTH__JWT__ACCESS_TTL_SECS=600. Lists are written in TOML syntax: RUSTCMS_HTTP__TRUSTED_PROXIES='["10.0.0.0/8"]'. With every value in the environment, the config/ directory is optional.

From files (Docker and Kubernetes secrets) ​

Any of these variables (the well-known ones and every RUSTCMS_…) can be read from a file instead: add _FILE to its name and give the path.

sh
export APP_KEY_FILE=/run/secrets/app_key
export DATABASE_URL_FILE=/run/secrets/database_url
export RUSTCMS_MAIL__SMTP__PASSWORD_FILE=/run/secrets/smtp_password
  • The value takes its variable's place in the order above: a RUSTCMS_DATABASE__URL still wins over DATABASE_URL_FILE.
  • One trailing line break is removed (as echo and editors add it); any other whitespace is kept. Values are read like environment values (true, numbers), except that a value with leading or trailing spaces stays exactly that string.
  • Boot fails when a variable and its _FILE are both set, or when the file is missing, unreadable, empty, not UTF-8 or larger than 64 KiB. The message names the variable and the path, never the content.
  • A key whose own name ends in _file cannot be set from the environment (RUSTCMS_X__LOG_FILE means the file of x.log); put it in a TOML file. A key named file itself is fine: RUSTCMS_LOG__FILE is log.file.

In tests, rustcms_testing::test_config(url) builds a configuration for a test database; change it with with (Testing).

Pitfalls ​

  • A section named like the framework's (mail, queue, storage, …) is the framework's: your fields and its fields must agree, and its checks apply.
  • .env does not override a variable already exported in the shell or by systemd: the environment wins.
  • Secrets in config/*.toml end up in the repository. Keep APP_KEY, database passwords and SMTP passwords in the environment or in _FILE secrets.
