Admin API

The admin panel talks to the server through a JSON API under <admin_path>/api (default /admin/api). You rarely call it yourself, but it is what resources expose, and its rules are the rules of every client: tests, scripts, a custom front end.

Every request uses the admin session (cookie) and, for writes, the CSRF token and an allowed Origin (Authentication). Responses, errors included, are Cache-Control: private, no-store; unknown paths under /api are JSON 404. Errors follow the standard format; values follow the wire format.

Options are available to users who may use the field. When a record-level policy hides more than 1,000 candidates before 50 visible ones are found, the endpoint answers 422 on search: refine the search. Edit and view forms send record=<key>: the record is loaded in the user’s scope and the policy decides on it (update with a writable field, or view with a readable one), exactly as for the form and the update. Without record: read the field with view_any, or write it with create or update. Which records appear is decided by the target resource’s scope and policy.

Lists

page, per_page (≤ 100), sort (title or -title), search (case-insensitive as the database folds case: Unicode on PostgreSQL, ASCII on SQLite; % and _ are literal), and filters filter[<field>][<op>]=<value> with op in eq, in, gt, gte, lt, lte. Values are read by field type: filter[published][eq]=true, filter[category_id][in]=1,2. JSON clients use the strict wire format.

trashed=with|only lists trashed records too, or only them, on resources with soft deletes (table.softDeletes); elsewhere it is a 422. It needs the restore or force_delete ability (schema abilities.restore / abilities.forceDelete), otherwise 403, and a trashed record is listed only if the policy allows view and restore or force_delete on it.

Records

{
  "key": "0199d3a4-…",
  "title": "Hello",
  "abilities": { "delete": true, "update": true, "view": true },
  "data": { "title": "Hello", "author_id": "7", "price": "10.50", "category_id": 1 },
  "labels": { "category_id": "News" }
}
  • data holds readable fields only, and is empty (no title, no labels) when the user may not view the record, e.g. the result of an update-only write.
  • abilities also holds one entry per action ("publish": true).
  • labels holds titles of related records. A related record the user may not see is shown as #<key>.
  • trashed: true marks a record in the trash (soft deletes; absent otherwise). Its abilities are view, restore and force_delete only; an active record of a soft-delete resource has restore and force_delete false.

Retrying writes safely

POST …/records (create) and POST …/actions/{action} accept an Idempotency-Key header (1–128 of A-Z a-z 0-9 _ -, otherwise 422 on idempotency_key). The key is claimed in the write’s transaction, so the write and its receipt commit together or not at all. Repeating the request with the same key, by the same user, within 24 hours:

  • same request (body compared canonically: key order does not matter) → the first result, not applied again: a create answers its record as the user may see it now (key only when no longer visible); an action answers the first run’s outcome with "replayed": true. Admission is checked again (403 if the user lost the ability). Action outcomes, first or replayed, list processed and denied keys only for records the user may view now;
  • different request → 422 on idempotency_key;
  • the first request still running → the retry waits (up to 5 s), then answers 409 write_conflict (nothing applied; retry later).

Keys are per user, resource and operation. At most 1,000 live keys per user (429 beyond). idempotency:prune deletes expired receipts (serve does it hourly). Updates and deletes take no key: repeating them converges.
