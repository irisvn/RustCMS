File storage ​

StorageProvider binds the configured storage: a local directory, or a private S3-compatible bucket. The media library, exports and imports keep their files there, and your own code can store files through the same Storage trait.

Quick start ​

Register the provider (the application template does):

rs
pub fn register(app: &mut AppBuilder, api: &ApiRoutes, admin: &AdminRoutes) {
    app.provider(providers::auth_service_provider::provider(api, admin));
    // Uploads under `storage/app` (see `[storage]`); the panel's media library uses them.
    app.provider(rustcms::storage::StorageProvider);
    app.provider(rustcms::mail::MailProvider);
    app.provider(providers::admin_panel_provider::provider());
    app.provider(providers::app_service_provider::AppServiceProvider);
}

With no [storage] section, files go to storage/app on the local disk. To use a bucket, build with the s3 feature and set:

toml
# config/storage.toml
disk = "s3"

[s3]
bucket = "my-app-media"
region = "eu-west-1"

Configuration ​

[storage] (config/storage.toml; every key can be overridden from the environment, e.g. RUSTCMS_STORAGE__DISK=s3, RUSTCMS_STORAGE__S3__BUCKET=…):

s3.timeout_secs30longest wait for a control request (exists, delete, opening a download), retries included (1 to 600)

S3 credentials come from the usual AWS_* variables (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY), never from the TOML files.

  • The type of an upload is detected from its content, not from its name or the client's Content-Type, and must be in allowed_types. SVG, HTML, XML and scripts are always refused, whatever allowed_types says.
  • Object keys are generated (yyyy/mm/<uuid>.<ext>), never taken from the client.
  • Boot panics on an invalid [storage] section, an unknown disk, or a disk that cannot be opened (a missing s3 feature, a bad root).

Drivers ​

  • local: files under storage.root. Every operation is anchored to that directory: no path, symbolic link or concurrent rename leads outside it. A file is written next to its target, synced, then renamed, so readers never see a partial file. Keep the directory out of the web root, back it up, and share it (one volume) when you run several instances.
  • s3 (feature s3): a private bucket on AWS S3 or any S3-compatible service (Cloudflare R2, MinIO, …). Set s3.endpoint for non-AWS services. Configure an abort incomplete multipart uploads lifecycle rule on the bucket (large files go up in parts; an upload interrupted by a crash leaves parts behind). Uploads are staged in <storage.root>/.s3-staging/ (created private to the app's user; a symbolic link there is refused) before they are sent; files left there by a crash (uploads, exports and imports being written) are removed after an hour by the instance's own sweep (serve, queue:work, media:prune).

toml

Create an R2 API token with Object Read & Write on that bucket only.

Other S3-compatible services ​

Set endpoint to the service's URL (path-style requests are used) and its region (often us-east-1). allow_http = true only for a local test server; production endpoints use HTTPS.

Failures ​

A bucket that does not answer fails a control request within s3.timeout_secs (retries included). Data moves under s3.transfer_timeout_secs per request: size it for your largest part (uploads go in 10 MiB parts) or download over the slowest link you accept. http.timeout_secs (408) bounds the whole HTTP request separately; keep it above s3.timeout_secs so a slow bucket shows as a 500, not a 408.

  • Before the response starts (an upload, or opening a download): the client gets 500, and the error's details (endpoint, key, credentials) go to the log only.
  • While a download streams: the connection is closed before the announced Content-Length is reached, so the client sees an incomplete download, never an error page inside the file.

Storing your own files ​

Use the bound storage from your own code: rustcms::storage::of(&state) returns it as an Arc<dyn Storage> (or None without StorageProvider). A sketch, storing a file you already wrote to disk and serving it later:

rust
use rustcms::storage::{self, StorageKey};

let storage = storage::of(&state).ok_or_else(|| AppError::internal("no storage bound"))?;

// Store: a fresh key, then the file's bytes under it (copied; delete your file afterwards).
let key = StorageKey::generate("pdf")?;
storage.put_file(&key, &path, "application/pdf").await?;
// Save `key.as_str()` in your row.

// Serve: validate the stored key again, then stream the object.
let (body, length) = storage.open(&StorageKey::parse(&row.file_key)?).await?;

StorageError converts to AppError with ?: a missing object is a 404, anything else a 500 whose details go to the log only.

Serving files is your responsibility

Your route decides who may read a file: check access before open, as for any record. Set the response headers yourself: a fixed Content-Type you detected when storing it, X-Content-Type-Options: nosniff, and Content-Disposition: attachment for anything a browser could render. Never build a key from client input: parse the key you stored.

Pruning ​

  • Files of deleted media and abandoned uploads are removed every minute by the rustcms.media-prune.<disk> schedule, and by rustcms media:prune (it stops taking new work after five minutes; the rest waits for the next run).
  • Exports and imports are removed every 10 minutes by the rustcms.exports-prune.<disk> schedule, or rustcms schedule:run rustcms.exports-prune.<disk>.
  • Each serve and queue:work removes the files it staged and abandoned (older than an hour) every 10 minutes.

Schedules run only in serve with the scheduler, once per slot across instances. See Data retention.

Files are always served through the application (no presigned URLs), so authorization and safe response headers apply to every byte.
