Database & migrations ​

RustCMS stores everything in one SQL database through SeaORM 2.0. SQLite, PostgreSQL and MySQL 8.4 are supported (MariaDB is not). This page covers models, migrations, seeders, factories, and the transactions and locks you need when several requests write the same rows.

Quick start ​

Set the connection in .env (Configuration):

sh
DATABASE_URL=sqlite://database.sqlite?mode=rwc
# DATABASE_URL=postgres://postgres:postgres@localhost:5432/blog
# DATABASE_URL=mysql://root:secret@localhost:3306/blog

Generate a model and the migration that creates its table, then run it:

sh
rustcms make:model Post -m      # src/models/post.rs + src/database/migrations/m…_create_posts_table.rs
rustcms migrate

The generator writes only the key and the timestamps; add your columns to both files:

rust
// src/models/post.rs
use sea_orm::entity::prelude::*;

#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel)]
#[sea_orm(table_name = "posts")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i64,
    pub created_at: DateTimeUtc,
    pub updated_at: DateTimeUtc,
}

#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}

impl ActiveModelBehavior for ActiveModel {}

Query models with SeaORM, using the pool from the state:

rust
let posts = post::Entity::find().filter(post::Column::Title.contains("rust")).all(state.db()).await?;

Models ​

Models are SeaORM entities in src/models/, one file per table. The demo's posts model, after a few migrations:

rs
#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel)]
#[sea_orm(table_name = "posts")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i64,
    pub title: String,
    pub body: Option<String>,
    pub category_id: Option<i32>,
    pub author_id: Option<i64>,
    pub published: bool,
    pub published_at: Option<DateTimeUtc>,
    pub created_at: DateTimeUtc,
    pub updated_at: DateTimeUtc,
    pub deleted_at: Option<DateTimeUtc>,
    pub cover: Option<Uuid>,
    pub content: Option<Json>,
    pub attributes: Option<Json>,
}

#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}

impl ActiveModelBehavior for ActiveModel {}

The framework's own tables come with the framework's migrations, which run before yours. Their entities live in rustcms::models: user, audit_log, job, job_receipt, job_run, schedule_run, schedule_slot, schedule_state and setting. Roles, permissions, sessions and tokens are in rustcms::auth::entities (Database schema). Change them only through their services (RbacService for roles and permissions), never with direct writes.

Every connection opened by rustcms::db::connect (the pool of serve, the console and the tests) is set up the same way:

  • SQLite: foreign keys on, WAL journal, 5 s busy timeout.
  • MySQL: UTC time zone and the utf8mb4_0900_bin collation (rustcms::db::MYSQL_COLLATION), whatever the URL says. See MySQL.
  • Pool size: database.max_connections (10). database.log_statements = true logs every SQL statement at debug level.

Migrations ​

src/database/migrations/mod.rs lists the framework's migrations (rustcms::migration::framework()) and then yours. rustcms make:migration <name> adds a file and registers it there:

rs
pub struct Migrator;

impl MigratorTrait for Migrator {
    fn migrations() -> Vec<Box<dyn MigrationTrait>> {
        let mut migrations = rustcms::migration::framework();
        let app: Vec<Box<dyn MigrationTrait>> = vec![
            Box::new(m20261011_155203_create_posts_table::Migration),
            Box::new(m20261012_000001_create_categories_and_post_content::Migration),
            Box::new(m20261013_000001_add_deleted_at_to_posts::Migration),
            Box::new(m20261014_000001_add_media_to_posts::Migration),
            Box::new(m20261014_000002_add_color_to_categories::Migration),
            Box::new(m20261015_000001_add_attributes_to_posts::Migration),
            Box::new(m20261022_000001_create_tags::Migration),
            Box::new(m20261101_000001_create_integrations::Migration),
            // rustcms:migrations
        ];
        migrations.extend(app);
        migrations
    }
}

A migration creating a table, as make:migration create_posts_table writes it:

rs
use rustcms::migration::*;

#[derive(DeriveMigrationName)]
pub struct Migration;

#[async_trait::async_trait]
impl MigrationTrait for Migration {
    /// Schema change and migration record commit together, also on SQLite
    /// (whose default is no transaction), so a failed run can be retried.
    fn use_transaction(&self) -> Option<bool> {
        Some(true)
    }

    async fn up(&self, manager: &SchemaManager) -> Result<(), DbErr> {
        create_table(
            manager,
            Table::create()
                .table(Posts::Table)
                .col(ColumnDef::new(Posts::Id).big_integer().not_null().auto_increment().primary_key())
                .col(ColumnDef::new(Posts::CreatedAt).instant_now(manager).not_null())
                .col(ColumnDef::new(Posts::UpdatedAt).instant_now(manager).not_null())
                .to_owned(),
        )
        .await
    }

    async fn down(&self, manager: &SchemaManager) -> Result<(), DbErr> {
        manager.drop_table(Table::drop().table(Posts::Table).to_owned()).await
    }
}

#[derive(DeriveIden)]
enum Posts {
    Table,
    Id,
    CreatedAt,
    UpdatedAt,
}

A migration adding a column:

rs
use rustcms::migration::*;

#[derive(DeriveMigrationName)]
pub struct Migration;

#[async_trait::async_trait]
impl MigrationTrait for Migration {
    fn use_transaction(&self) -> Option<bool> {
        Some(true)
    }

    /// Soft deletes for posts: deleting sets `deleted_at` (see `PostResource`).
    async fn up(&self, manager: &SchemaManager) -> Result<(), DbErr> {
        add_column(manager, Posts::Table, ColumnDef::new(Posts::DeletedAt).instant(manager).null()).await
    }

    async fn down(&self, manager: &SchemaManager) -> Result<(), DbErr> {
        drop_column(manager, Posts::Table, Posts::DeletedAt).await
    }
}

#[derive(DeriveIden)]
enum Posts {
    Table,
    DeletedAt,
}

Keep use_transaction() -> Some(true) in every migration, as the generators write it. The schema change and the migration record then commit together, also on SQLite (whose default is no transaction): a failed migration leaves no partial schema and can run again. Leave it out only for a statement that cannot run in a transaction. MySQL is different: each DDL statement commits on its own, so write migrations that can run again (the helpers below skip what exists).

Commands ​

CommandDoes
rustcms migrateapplies pending migrations
rustcms migrate --allow-neweralso accepts migrations applied by a newer binary (they are logged and left alone)
rustcms migrate:statuslists each migration as Applied, Pending or Newer (applied, unknown to this binary)
rustcms migrate:rollback --step Nundoes the last N (default 1), in the migrator's order
rustcms migrate:refresh [--force]undoes every migration, then applies all
rustcms migrate:fresh [--force] [--seed]drops every table, applies all, then runs the database seeder with --seed
  • migrate:refresh and migrate:fresh refuse in production without --force.
  • migrate, migrate:rollback, migrate:refresh and migrate:fresh run on a single connection (rustcms::db::connect_for_migrations): with a pool, other SQLite connections could still see the old schema between steps.
  • migrate:fresh turns SQLite foreign keys off while it drops the tables, then back on.
  • migrate refuses migrations it does not know, unless --allow-newer or [database] allow_newer_migrations = true. That is safe only when the newer migrations are additive (new tables, nullable columns).

migrate:rollback undoes migrations last first in the migrator's order (the framework's, then yours), not in the order they were applied: after a RustCMS upgrade that added framework migrations, --step 1 undoes your newest migration, not the framework's. To run an older binary on a newer schema, keep the migrations and use migrate --allow-newer: see Upgrading.

Never edit a migration that has run in production; add a new one. A migration that cannot be reversed must say so in its down and in its doc comment.

Column helpers ​

rustcms::migration re-exports SeaORM's migration prelude and adds helpers that build the same table on every database and skip what a previous run did:

HelperDoes
create_table(manager, statement)IF NOT EXISTS; on MySQL: InnoDB, utf8mb4_0900_bin
create_index(manager, table, statement)skips an index the table has (MySQL ignores IF NOT EXISTS on indexes)
add_column(manager, table, column)skips a column that exists
drop_column(manager, table, column)skips a column that is gone
drop_table(manager, table)skips a table that is gone
.instant(manager)an instant: TIMESTAMPTZ on PostgreSQL, DATETIME(6) (UTC) on MySQL
.instant_now(manager)the same, defaulting to the current time
.local_date_time(manager)date and time without zone, microseconds on MySQL

instant, instant_now and local_date_time come from the ColumnDefExt trait, which use rustcms::migration::* brings in.

MySQL ​

Create the database with the collation RustCMS needs, so text compares as on PostgreSQL (case, accents and trailing spaces all count):

sql
CREATE DATABASE app CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_bin;

The app builder (so serve and every command that boots the application), migrate, migrate:rollback, migrate:refresh and migrate:fresh check the database first (rustcms::db::check) and refuse to start when:

  • the database default, or any string column, uses another character set or collation (migrate:refresh and migrate:fresh check only the database itself, since they recreate every table);
  • a table is not InnoDB;
  • sql_mode (global or session) is not strict (STRICT_TRANS_TABLES) or has NO_BACKSLASH_ESCAPES;
  • the connection is not in UTC with that collation (pools opened with rustcms::db::connect always are).

The error lists the SQL that fixes each problem. migrate:status only reads and does not run the check.

Differences to know:

  • DDL is not transactional: each statement commits. A migration that fails half-way is retried on a partly changed schema. Use the helpers above, which skip what exists, and stop writers while migrating.
  • Column types: a bare String field is varchar(255) (PostgreSQL: unbounded); Text holds 64 KiB. JSON columns accept no literal default (only an expression default such as ('[]')).
  • Sort order of text is binary (code points), not a locale.
  • Instants are DATETIME(6) in UTC (MySQL's TIMESTAMP stops in 2038 and drops fractions); fractions below a microsecond are truncated.
  • Write transactions run in READ COMMITTED, as on PostgreSQL, and wait at most 10 s for a row lock (see below).
  • Named locks (xact_lock) accept only the framework's own names: lock rows instead (see Named locks).

Transactions and locks ​

Use rustcms::db::begin_write for every transaction that writes. It behaves the same on the three databases:

Databasebegin_write
SQLiteBEGIN IMMEDIATE: takes the write lock at once, so a concurrent writer waits for the busy timeout instead of failing with "database is locked" when a read turns into a write
PostgreSQLa plain transaction (READ COMMITTED)
MySQLREAD COMMITTED, and the session's row lock wait reset to MYSQL_LOCK_WAIT_SECONDS (10)

A transaction that waits too long for a lock, or that deadlocks, fails and becomes a 409 write_conflict with reason: "busy" (Errors): nothing was saved and the client may retry.

To keep a rule that reads other rows ("no more enrollments than seats"), lock the parent row first. The LMS example locks the course, then checks and writes in the same transaction:

rs
/// Locks the course's row until `txn` ends (SQLite: the write transaction
/// already holds the database lock).
pub async fn lock_course(txn: &DatabaseTransaction, course_id: i64) -> AppResult<Option<course::Model>> {
    let select = course::Entity::find_by_id(course_id);
    let select = if txn.get_database_backend() == DbBackend::Sqlite { select } else { select.lock_exclusive() };
    Ok(select.one(txn).await?)
}
rs
/// Enrolls `learner_id` in `course_id` (active) in a transaction of its own,
/// queuing the welcome with it. For code outside the admin panel (seeders,
/// jobs, an API).
pub async fn enroll(
    db: &DatabaseConnection,
    course_id: i64,
    learner_id: i64,
) -> AppResult<Result<enrollment::Model, Refusal>> {
    let txn = rustcms::db::begin_write(db).await?;
    lock_course(&txn, course_id).await?;
    match enroll_in(&txn, course_id, learner_id).await? {
        Ok(created) => {
            txn.commit().await?;
            Ok(Ok(created))
        }
        Err(refusal) => {
            txn.rollback().await?;
            Ok(Err(refusal))
        }
    }
}

SQLite has no row locks: the write transaction already holds the whole database, which is why lock_course skips lock_exclusive there. When a write locks rows of several tables, lock parents before children, and keys in key order, as the admin panel does (Resources).

FunctionDoes
begin_write(db)a write transaction, as above
begin_snapshot(db)a read-only transaction whose reads all see one snapshot (REPEATABLE READ on PostgreSQL and MySQL; on SQLite in WAL mode a read transaction keeps the snapshot of its first read), for scans in several queries
set_lock_wait(&txn, seconds)MySQL only: this session's row lock wait (at least 1 s); begin_write restores the default

Named locks ​

RustCMS serializes some of its own work with rustcms::db::xact_lock(&txn, name) (advisory locks on PostgreSQL, rows of the rustcms_locks table on MySQL, nothing extra on SQLite). It is public, but it is not a general lock for application code:

On MySQL, only the framework's names exist

On MySQL, xact_lock locks a row of rustcms_locks, which holds only the framework's own names (rbac, and the slots of its lineage and idem namespaces, the names rustcms::db::lock_slot produces). Any other name fails there with lock `…` is missing from rustcms_locks (a 500), while the same code works on PostgreSQL and SQLite. An application cannot add names, and the framework's names are not part of the public API: do not borrow them.

In application code, serialize with row locks inside a write transaction, as lock_course does above: lock the row the rule is about (a parent, an account, a counter row you create for the purpose) with lock_exclusive() on PostgreSQL and MySQL, and rely on begin_write's database lock on SQLite. This works the same on the three databases, and the lock ends with the transaction.

Seeding ​

Seeders fill the database with the records an application needs, or shows off. They live in src/database/seeders/: DatabaseSeeder (named database) calls the others in order with rustcms::database::call, and every seeder is registered on the app builder. rustcms make:seeder CourseSeeder writes the file, registers it and adds it to DatabaseSeeder.

rust
use rustcms::database::Seeder;
use rustcms::{AppState, async_trait};

pub struct CourseSeeder;

#[async_trait]
impl Seeder for CourseSeeder {
    fn name(&self) -> &'static str {
        "course" // `rustcms db:seed --class course`
    }

    async fn run(&self, state: &AppState) -> anyhow::Result<()> {
        // Find by a natural key before creating: seeders run again.
        Ok(())
    }
}

The demo registers its seeders in AppServiceProvider::register:

rs
// `rustcms db:seed` runs `database` (it calls the others).
app.seeder(seeders::DatabaseSeeder);
app.seeder(seeders::user_seeder::UserSeeder);
app.seeder(seeders::category_seeder::CategorySeeder);
app.seeder(seeders::post_seeder::PostSeeder);

A seeder that creates roles goes through RbacService, and finds each role before creating it, so it can run again:

rs
pub struct RoleSeeder;

#[async_trait]
impl Seeder for RoleSeeder {
    fn name(&self) -> &'static str {
        "role"
    }

    async fn run(&self, state: &AppState) -> anyhow::Result<()> {
        let auth = state.service::<AuthState>().expect("AuthProvider");
        let rbac = RbacService::new(state.db(), &auth.resolver);
        rbac.sync_permissions(&auth.permissions.all()).await?;
        let roles = [("staff", STAFF), ("instructor", INSTRUCTOR), ("editor", EDITOR), ("viewer", VIEWER)];
        for (name, permissions) in roles {
            if find(state, name).await?.is_none() {
                let permissions: Vec<String> = permissions.iter().map(|p| (*p).to_owned()).collect();
                rbac.create_role(Actor::System, ADMIN_GUARD, name, &permissions).await?;
            }
        }
        Ok(())
    }
}
CommandDoes
rustcms db:seedruns the database seeder (rustcms::database::DEFAULT_SEEDER)
rustcms db:seed --class courseruns one seeder
rustcms migrate:fresh --seeddrops every table, migrates, seeds

  • Names: 1–64 characters of a-z, 0-9 and _. app.seeder(…) panics on an invalid name or a name registered twice. AppBuilder::seeders() returns what is registered.

  • Production: db:seed refuses without --force. A seeder that creates accounts with known passwords must refuse in production itself, whatever --force says:

    rs
    /// Well-known passwords and a super admin: never in production, whatever
/// `db:seed --force` says.
pub fn refuse_in_production(state: &AppState) -> anyhow::Result<()> {
    if state.config().app.env == rustcms::config::Environment::Production {
        anyhow::bail!("the demo seeders create accounts with a public password; refusing in production");
    }
    Ok(())
}

  • No shared transaction: a seeder that fails halfway leaves what it wrote. Write seeders that complete on the next run (find rows by a natural key), and write through your services (which open their own transactions) so the application's rules hold.

  • db:seed boots the whole application first, so every provider's boot runs (see Console).

Factories ​

A factory builds records from a definition, for seeders and tests (Laravel's model factories). rustcms make:factory Course writes src/database/factories/course_factory.rs; fill in definition:

rs
use rustcms::database::Factory;
use sea_orm::ActiveValue::Set;

use crate::models::course;

#[derive(Default)]
pub struct CourseFactory {
    capacity: Option<i32>,
    instructor: Option<i64>,
}

impl CourseFactory {
    pub fn new() -> Self {
        Self::default()
    }

    /// Active enrollments allowed (default 30).
    pub fn capacity(mut self, capacity: i32) -> Self {
        self.capacity = Some(capacity);
        self
    }

    /// Taught by the user `id`.
    pub fn taught_by(mut self, id: i64) -> Self {
        self.instructor = Some(id);
        self
    }
}

impl Factory for CourseFactory {
    type Entity = course::Entity;

    fn definition(&self, n: u64) -> course::ActiveModel {
        course::ActiveModel {
            title: Set(format!("Course {n}")),
            slug: Set(format!("course-{n}")),
            summary: Set(None),
            capacity: Set(self.capacity.unwrap_or(30)),
            published: Set(true),
            instructor_id: Set(self.instructor),
            created_at: Set(chrono::Utc::now()),
            ..Default::default()
        }
    }
}
Method of rustcms::database::FactoryDoes
definition(&self, n)the column values of record number n; required
try_create(db) / try_create_many(db, count)inserts, returning Result<_, DbErr> (seeders)
create(db) / create_many(db, count)inserts, panicking on a database error (tests)

n is unique per process, so use it in unique columns (slug, email). Builder methods such as capacity(1) above are yours to add. db is any SeaORM connection, a transaction included. In tests, rustcms_testing::Factory is the same trait (Testing).

Pitfalls ​

  • Writing without begin_write on SQLite: a transaction that reads and then writes can fail with "database is locked" under load.
  • Using xact_lock with a name of your own: it works on PostgreSQL and SQLite and fails on MySQL. Lock rows instead (see Named locks).
  • A String column is varchar(255) on MySQL: longer values fail there only.
  • migrate:rollback --step N follows the migrator's order, not the order migrations ran.
