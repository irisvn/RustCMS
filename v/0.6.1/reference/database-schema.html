RustCMS

Database schema

The framework’s migrations (rustcms::migration, run by rustcms migrate before your own) create the tables below. Your models live next to them in the same database. Column types are shown portably:

  • instant: TIMESTAMPTZ on PostgreSQL, DATETIME(6) in UTC on MySQL, text on SQLite;
  • bigint id: auto-increment BIGINT.

Never write the access-control tables yourself: every change to roles, permissions and their assignments goes through RbacService (Roles & permissions), which checks the actor, locks, audits and invalidates the permission cache.

                     (role_id, permission_id)

A user’s permissions in a guard are those of their roles in that guard, plus their direct grants. Orphaned permissions are left out. super_admin passes every check of its guard.

Deleting a user cascades to their tokens, JWT families and one-time tokens. Their role and permission assignments are removed by RbacService in the same transaction: model_has_* hold no foreign key to users.

Rows come from the permissions the application declares (resources, AuthProvider::permission). rustcms permission:sync adds the new ones and marks the undeclared ones orphaned. It never renames or deletes, so a typo cannot silently drop a grant.

role_has_permissions, model_has_roles, model_has_permissions

TablePrimary keyForeign keys
role_has_permissions(role_id, permission_id)both, ON DELETE CASCADE
model_has_roles(role_id, model_type, model_id)role_id → roles, cascade
model_has_permissions(permission_id, model_type, model_id)permission_id → permissions, cascade
  • model_type is user and model_id is the user’s id as text: the Spatie-style shape leaves room for other holders.
  • model_has_* are indexed on (model_type, model_id) for “what does this user hold”.
  • Direct grants (model_has_permissions) exist for exceptions; roles are the usual way.

auth_generations

ColumnTypeNotes

Instances cache resolved permissions per generation. A change anywhere advances it, and every instance reloads (several instances).

A copy of these tables gives nobody a working credential: only hashes are stored. Restoring a backup still requires ending every sign-in (backup and restore).

Reading them

For reports or support, read-only SQL is fine. For example, everyone holding a permission in the admin guard:

SELECT DISTINCT u.id, u.email
FROM users u
JOIN model_has_roles mr ON mr.model_type = 'user' AND mr.model_id = CAST(u.id AS CHAR(20))
JOIN roles r ON r.id = mr.role_id AND r.guard_name = 'admin'
LEFT JOIN role_has_permissions rp ON rp.role_id = r.id
LEFT JOIN permissions p ON p.id = rp.permission_id AND p.orphaned = FALSE
WHERE p.name = 'posts.update' OR r.name = 'super_admin';

(Direct grants: the same through model_has_permissions. On PostgreSQL, use CAST(u.id AS TEXT).) Writes go through RbacService or the System pages.
