Scheduling ​

Periodic work (reconcile every minute, prune every night, a daily digest) is declared on the application with app.schedule and run by rustcms serve. Each slot runs once for the whole deployment, however many instances you run, without Redis or an external cron.

Quick start ​

Declare schedules while the application is assembled: in a provider's register, or in a function the bootstrap calls. register returns (), so a cron expression is unwrapped with .expect(..), not ?: a typo then stops the boot with a clear message.

rust
use std::time::Duration;
use rustcms::schedule::Schedule;

// Every hour, as a queue job:
app.schedule(Schedule::every("posts-ping", Duration::from_secs(3600)).job(|| PingPosts));
// Every day at 03:00 UTC, in the process:
app.schedule(
    Schedule::cron("cleanup", "0 3 * * *")
        .expect("a valid cron expression")
        .run(|state| async move { cleanup(&state).await }),
);

Full example ​

The demo keeps its schedules next to their job, in src/jobs/post_digest.rs:

rs
/// The demo's schedules.
pub fn schedule(app: &mut AppBuilder) {
    app.schedule(Schedule::every("posts-ping", Duration::from_secs(3600)).job(|| PingPosts).without_overlapping());
    app.schedule(
        Schedule::cron("posts-digest", "0 6 * * *")
            .expect("a valid cron expression")
            .task(|ctx| async move {
                let posts = post::Entity::find().count(ctx.state.db()).await?;
                Ok(Some(format!("{posts} posts")))
            })
            .timeout(Duration::from_secs(60)),
    );
}

The bootstrap calls it after the providers:

rs
/// The application for `config`: its providers, then its API routes.
pub fn build(config: Config) -> AppBuilder {
    let mut app = AppBuilder::new(config);
    let api = crate::routes::api::routes();
    let admin = crate::routes::admin::routes();
    providers::register(&mut app, &api, &admin);
    crate::jobs::post_digest::schedule(&mut app);
    // Mounted and listed by `rustcms route:list` from the same declarations.
    api.register(&mut app);
    admin.register(&mut app);
    app
}
  • posts-ping enqueues the PingPosts job every hour, and skips a slot while the previous one's job is still pending or running.
  • posts-digest runs a task every day at 06:00 UTC, stopped after a minute, and its summary ("12 posts") shows on the Schedules page.

The job it enqueues:

rs
/// Counts the posts (a stand-in for real work).
#[derive(Serialize, Deserialize)]
pub struct PingPosts;

#[async_trait]
impl Job for PingPosts {
    const KIND: &'static str = "demo.ping_posts";

    fn describe(&self) -> Option<String> {
        Some("count the posts".into())
    }

    async fn handle(self, ctx: JobCtx) -> anyhow::Result<()> {
        post::Entity::find().count(ctx.state.db()).await?;
        Ok(())
    }
}
In a real application: RDockPanel's backups

RDockPanel, a hosting panel built on RustCMS, checks every minute which backups are due and queues them; the summary shows on the Schedules page (src/providers/app_service_provider.rs, v0.9.3):

rust
app.schedule(
    rustcms::schedule::Schedule::every("database-backups", std::time::Duration::from_secs(60))
        .task(|ctx| async move {
            let n = crate::services::backup_service::tick(&ctx.state).await?;
            Ok((n > 0).then(|| format!("{n} backups queued")))
        }),
);

When it fires ​

  • Schedule::every(name, period): 10 s to 7 days, whole seconds, on the multiples of the period since the Unix epoch. Every instance agrees on the times (a minute schedule fires at :00 of every minute).
  • Schedule::cron(name, "m h dom mon dow"): five fields in UTC, so there are no time zones and no daylight saving time.
    • Numbers, *, ranges, lists, steps and 3-letter names (MON, JAN) are accepted.
    • Day-of-month and day-of-week combine with OR, as in Vixie cron.
    • No seconds, years, L, W, # or @daily.
    • It returns Result<Schedule, ScheduleError>: ScheduleError::Cron for an expression it cannot read, ScheduleError::Never for one that never fires in the next five years (0 0 30 2 *).
  • A missed slot is skipped, never caught up: after a restart or a pause only the next slot runs. A slot is still taken up to schedule.grace_secs (30) late.
  • Names are 1–64 of a-z 0-9 _ . -, unique; rustcms. is reserved for the framework's schedules.

What it does ​

Give each schedule exactly one action.

  • .job(make) (recommended) enqueues a queue job for each slot. The job's retries, timeouts and leases apply, and the Queue page shows it.
    • It registers the job type; app.job::<J>() as well is fine.
    • Workers must serve its queue (serve, or queue:work).
  • .run(f) runs f(state) in the process. It is best effort: a crash during the run loses it. Its error is recorded as "failed (see the logs)".
  • .task(f) is .run with a context and a result the Schedules page shows (the demo's posts-digest above).
    • Ok(Some(summary)) is kept (at most 200 characters); Ok(None) keeps none.
    • An error whose chain holds a queue::Failure keeps its message; any other error is kept as "failed (see the logs)".
    • schedules.view holders see both: never put secrets in them.
    • Moving from .run: |state| becomes |ctx| (ctx.state), Ok(()) becomes Ok(None).
  • .timeout(d) bounds a .run or .task (default 1 hour, at most a day): a longer run is stopped and recorded as failed. A .job schedule uses the job's own timeout().
  • Once per slot, whatever the number of instances. Each slot is claimed in the database, in the same transaction as its job, so there is at most one job per slot (no Redis needed). Jobs are still at-least-once: make them idempotent.

TaskCtx, what a .task receives:

Field
statethe AppState
run_idthis run (schedule_runs.id): stable, a key for your own idempotency
triggerTrigger::Schedule (its slot came) or Trigger::Manual (Run now, schedule:run)
initiated_bythe user who ran it, for a manual run by a user

Overlapping runs ​

  • A .job schedule enqueues a job per slot. If one can take longer than the period, add .without_overlapping(): a slot is skipped while the previous slot's job is still pending or running. The queue's lease is the lock, so a dead worker's job is retried, then the schedule resumes.
  • A .run or .task schedule never overlaps itself on one instance (slots are skipped). On several instances two long runs can overlap: use .job + .without_overlapping() instead.
  • Manual runs from the console (schedule:run) and queue:retry are not held back. The panel's Run now is (see below).

Where it runs ​

  • Only serve runs the schedules. Console commands, queue:work and tests (TestApp) never do.
  • [schedule] enabled = false turns it off on an instance (for example on instances that only serve requests).
  • Instances' clocks must agree within about a second (NTP). A clock running fast can start a slot that much early; it never runs a slot twice.
  • On shutdown nothing new starts, and .run and .task actions get [realtime] shutdown_grace_secs, then are stopped.

Configuration ​

[schedule] (config/schedule.toml, or RUSTCMS_SCHEDULE__<KEY>):

KeyDefaultRange
enabledtrue (false in API mode)run the schedules in serve on this instance; a value set wins over the mode
grace_secs301 to 300how late a slot may still be claimed
history_retention_days71 to 3,650how long runs are kept in schedule_runs

Boot fails on a value out of range.

Commands ​

sh
rustcms schedule:list              # each schedule, its next slot, its last claimed slot (and job)
rustcms schedule:run posts-digest  # run it now: a job is enqueued, a task runs in the command

A manual run is not a slot: there is no claim, no grace and no without_overlapping, and enabled is ignored. It is recorded as a manual run.

The Schedules page ​

The demo application: System → Schedules, with posts-ping and posts-digest.

RDockPanel, a hosting panel built on RustCMS: its periodic work (backups, certificate expiry, health alerts) as schedules.

System → Schedules lists every schedule to users with schedules.view: its rule, what it does (a job kind or a task), its next run, and its last run (status, when, how long, a task's summary or error). Clicking a name opens its recent runs. It refreshes like the Queue page.

Each run is recorded in schedule_runs (kept [schedule] history_retention_days, 7 by default; pruned by the scheduler and by queue workers):

StatusMeaning
dispatcheda job schedule's job (or Run now's) is waiting or running
runninga closure is running in serve
succeeded, failedit ended; a job schedule's outcome is written by its job's own transition
skippedwithout_overlapping held the slot back
cancelledits job was cancelled on the Queue page
unknownits end was not recorded (a shutdown, a crash: a running run older than its timeout plus an hour shows so)

Run now (users who also hold schedules.manage) runs a schedule once, as a manual run, after a confirmation; it is recorded in the audit log (schedule.run). It goes through the queue, so a worker must run somewhere:

  • a job schedule enqueues its job on behalf of the user; with without_overlapping it is refused (409) while the previous job is pending or running;
  • a .run or .task schedule enqueues the framework's job rustcms.schedule.run, which runs the closure once in a worker, within the schedule's timeout and at most queue.max_timeout_secs: never retried, and a run stopped by a shutdown or a crash is recorded as failed, not run again. It is refused (409) while another run of the schedule is unfinished: a Run now whose job is still waiting or running, or a scheduled run younger than its timeout plus the grace. While a Run now's job is unfinished, the schedule's own slots are skipped (skipped). Two scheduled runs of adjacent slots may still overlap each other, as before.

The next scheduled run is unchanged. Both permissions are declared by the admin panel (group schedules); grant them through roles.

Schedule::cron(name, expr)Result<Schedule, ScheduleError>

schedule::MIN_PERIOD, MAX_PERIOD, DEFAULT_TIMEOUT10 s, 7 days, 1 hour

app.schedule panics at boot on an invalid, reserved or repeated name, a schedule without an action, or without_overlapping on a .run or .task schedule.

Pitfalls ​

  • Schedule::cron(..)? does not compile in register (it returns ()): use .expect("a valid cron expression").
  • Cron times are UTC: 0 6 * * * is 06:00 UTC, not local time.
  • Run now needs a queue worker even for a .task schedule.
  • Each instance sweeps its own staged files (serve, queue:work): that sweep is not a schedule and does not appear on this page. See Data retention.

Framework schedules ​

The framework registers its own schedules, named rustcms.… (the prefix is reserved: an application's rustcms.x panics at boot):

ScheduleEveryDoesSummary
rustcms.auth-prunehour (timeout 30 min)deletes expired sessions, ended JWT sign-ins, expired reset and invitation links, audit entries past audit.retention_days3 sessions, 0 JWT sign-ins, 1 links, 0 audit entries
rustcms.idempotency-prunehour (timeout 30 min)deletes expired idempotency receipts of admin writes12 expired keys
rustcms.media-prune.<disk>minute (timeout 30 min; only with .media())deletes files of deleted media and abandoned uploads of the storage's disk (local, s3)2 media files deleted
rustcms.exports-prune.<disk>10 minutes (timeout 30 min; with a storage)deletes expired exports and imports of the disk, with their files; each part runs (10 min at most) even when the other fails1 expired exports, 0 expired imports

They behave like yours: only serve runs them, once per slot across instances; they are listed on System → Schedules and by schedule:list, and schedules.manage can Run now (audited). Each part of the auth cleanup runs even when another fails; the run then fails with prune_failed: some cleanups failed (see the logs). Without serve (or with [schedule] enabled = false everywhere), run them from cron with schedule:run rustcms.auth-prune or the prune commands (Data retention).
