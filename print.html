RustCMS

Introduction

RustCMS is a Rust framework for building admin panels, back-offices and headless CMS backends. It takes its ideas from Laravel (applications, service providers, an artisan-like console, migrations, testing helpers) and Filament (resources that describe forms, tables and actions, rendered as a complete admin panel).

You describe your data in Rust:

impl Resource for PostResource {
    type Entity = post::Entity;
    const SLUG: &'static str = "posts";

    fn meta() -> ResourceMeta {
        ResourceMeta::new("Post").title("title").group("Content").soft_deletes()
    }

    fn fields() -> Vec<Field> {
        vec![
            Field::column(post::Column::Title).required().searchable().sortable(),
            Field::column(post::Column::CategoryId).belongs_to("categories").filterable(),
            Field::column(post::Column::Published).updatable(|ctx| ctx.can("posts.publish")),
        ]
    }
}

and RustCMS serves an authorized admin panel and JSON API for it, compiled into one binary: no Node, PHP or separate frontend to deploy.

What you get

  • Admin panel: lists with search, filters, sorting and bulk actions; forms with sections, tabs, relationships, file uploads, rich text and key/value inputs; soft deletes; has-many relation managers; custom field widgets; users, roles and account pages; English and Vietnamese.
  • Security by default: deny-by-default permissions per resource, record and field; scopes (tenancy, ownership) applied on every path; admin sessions with CSRF and origin checks; API tokens and JWT with immediate revocation; rate limits.
  • Application layer: typed configuration, service providers and a container, an HTTP stack with sane limits, JSON APIs with declared access, validation and pagination, SQLite, PostgreSQL and MySQL, file storage (local or S3-compatible), several instances with Redis.
  • Tooling: rustcms new, generators (make:model, make:resource, make:api, …), migrations, and a testing kit that runs every database test on all three databases.

Release notes

RustCMS is in pre-release. The current version is 0.4.0 (“panel platform”); 0.1.0-alpha.0 was the first published one.

0.4.0

  • Admin routes: JSON routes for your own panel pages under {admin}/api/x, on the admin session, each with a declared AdminAccess checked before extractors (AdminRoutes, AuthProvider::admin_permissions); assert_access tests every route against a table of actors (Admin routes).
  • Server-sent events: AdminRoutes::events streams live data to a page.
    • It is rechecked while open: the session, the user, the permissions and a per-target check.
    • Limits are per user and per instance, slow clients are dropped, and streams end cleanly on shutdown.
    • A process-local Hub shares one producer between viewers, with resync when a viewer falls behind.
    • Script pages read streams with ctx.realtime.events (Realtime).
  • WebSocket: AdminRoutes::socket for terminals and consoles.
    • Admission: the exact Origin and the session’s CSRF token as a subprotocol.
    • A supervised, rechecked socket with bounded queues both ways.
    • AdminSocket::authorize() checks a command when it runs.
    • Script pages use ctx.realtime.socket (Realtime).
  • Content Security Policy: unchanged, except that connect-src also names the panel’s own ws(s):// origins.
  • Secrets from files: every variable also reads <VAR>_FILE (Docker and Kubernetes secrets) (Configuration).
  • Testing: TestApp::new takes a closure, so tests can bind doubles. RUSTCMS_TEST_BACKENDS picks the databases, and TestClient::socket opens WebSocket connections (Testing).
  • Tooling: the test servers run in memory (the matrix is about twice as fast), and just test-fast runs every test on SQLite only.

  • Example: examples/lms grows news (categories, tags, scheduled articles), editor and viewer roles, lessons moved up and down, a dashboard, welcome mails and instructor invitations (An LMS back office).
  • Operations: running the queue, retention, backup and restore, rotating APP_KEY, running mail (Operations).

Upgrade guide

Upgrading the command and an application

  1. The command: rustcms self-update replaces it with the latest release (--version v0.4.0 for a given one, older included). It works when the install script installed it; a command built with cargo install is updated the same way it was installed. rustcms --version shows the version and the platform.

  2. An application: in its directory, rustcms upgrade moves it to the command’s version:

    rustcms upgrade --dry-run   # what changes in Cargo.toml
rustcms upgrade             # writes it, then updates Cargo.lock
rustcms migrate
cargo test

    It sets the tag of rustcms and rustcms-testing (always the same), the sea-orm pins of that version and [package.metadata.rustcms] version, keeping your comments and features. If Cargo cannot resolve the result, Cargo.toml and Cargo.lock are put back. It refuses to go back to an older version (unless --force), and leaves alone a dependency on a local path, inherited from a workspace, renamed, or from another repository: change those by hand. Then follow the section of that version below, and commit Cargo.toml and Cargo.lock together.

    To upgrade to another version than the command’s, install that command first (rustcms self-update --version vX.Y.Z).

From 0.3.2 to 0.4.0

rustcms self-update, then rustcms upgrade in each application. Nothing needs to change in your code.

  • New [realtime] keys, all optional: socket_revalidate_secs, max_message_bytes, send_timeout_secs (Configuration). The other keys already existed.
  • The admin page’s CSP now also lists ws(s):// for the panel’s origins in connect-src. A test that compares the header with rustcms::admin::spa::CONTENT_SECURITY_POLICY should use content_security_policy(&origins) instead.
  • {admin}/api/x belongs to your AdminRoutes: nothing built in lives there.
  • Behind a proxy, if you add WebSocket routes, see the production checklist.

From 0.3.1 to 0.3.2

Only the command changed (new doctor, upgrade, self-update, docs). Install it again with the install script (0.3.1 has no self-update), then rustcms upgrade in each application.

Applications made before 0.3.1

They depend on rustcms = "0.3.0" (not on crates.io) or on a local path. rustcms upgrade moves a version dependency to the Git tag; a path is changed by hand, keeping your features:

[dependencies]
rustcms = { git = "https://github.com/irisvn/RustCMS-Core", tag = "v0.3.1" }

[dev-dependencies]
rustcms-testing = { git = "https://github.com/irisvn/RustCMS-Core", tag = "v0.3.1" }

From 0.1.0-alpha.0 (or a 0.2 build) to 0.3.0

  1. Update the rustcms dependency, then run rustcms migrate (new tables for media, JWT sign-ins, idempotency keys, locks, the audit log, settings, jobs, and users.locale). serve now also runs queue workers (set queue.enabled = false to keep them out of web instances).
  2. Rust API changes:
    • API routes: move them to ApiRoutes with an explicit Access per route (Routing); register them with AuthProvider::new().api_permissions(&api) and api.register(&mut app).
    • RateLimiter::reserve, release and clear are async (.await them).
    • Principal and rustcms::models::user::Model have new fields (locale, credential): struct literals need them, or ..Default::default().
    • AppError::Conflict has a new reason field.
    • SettingsAbilities has a new test field; SettingsPage::validate_in (with the application) runs validate by default.
    • rustcms::models::user::Model has invitation_pending, invited_at, invited_by (migrations …000018, …000019): struct literals need them (..Default::default() on ActiveModels is unaffected). rustcms-auth now enables the core mail feature.
    • Mail: register rustcms::mail::MailProvider (and AdminProvider::mail_settings() for the page); in production with driver = "smtp" and source = "settings", set [mail] allowed_hosts.
    • Functions that change credentials record an audit entry and take one more argument: credentials::change_password and credentials::logout_everywhere an &AuditContext; credentials::issue_token and jwt_session::{issue, rotate, logout} a &RequestMeta (both in rustcms::audit; RequestMeta is also an extractor).
    • InputType has a Secret variant and AdminPanel a settings field (exhaustive matches and struct literals need them); admin clients see vocabularyVersion 5.
    • Resource slugs are limited to 64 bytes and action names to 57, and user, role, permission, settings, session (and job, queue, see below) are reserved (boot fails); Ctx::new records writes as its principal.
    • ActorKind has a Job variant (exhaustive matches need it).
    • AdminPanel has a custom field (CustomPanel::empty(base) in hand-built panels), PanelResponse a pages field and ColumnSchema cell / props; admin clients see vocabularyVersion 6.
    • SystemLinks has audit and queue fields; resource schemas gain the history ability.
    • Resource slugs job and queue are reserved too (subjects of the Queue page’s audit entries).
    • Actions: data sent to an action without a form is refused (422), and the request body may only hold keys and data. Declare what an action needs with Action::form (Actions). Actions are admitted before the body is read: a policy deciding per record should override Policy::admits for abilities that need a permission. Actions the policy does not admit are no longer listed in the schema.
    • Run rustcms migrate (new exports and imports tables). ResourceSchema.abilities may hold export; DynResource has new methods (implementations outside the crate are not expected).
    • Relation has new fields and RelationSchema a kind; ActionSchema a form; ListQuery a hidden through field (struct literals need ..Default::default()). Admin clients see schemaVersion 2 and vocabularyVersion 7: an older admin SPA turns read-only.
    • Tests that build tables from entities instead of running migrations also need the audit_logs table (Testing).
  3. Optional: translate your labels. Add lang/vi.toml, register it with AdminProvider::new().translations("vi", include_str!("../lang/vi.toml")), and fill in what rustcms lang:missing vi lists.
  4. API clients: error bodies gain issues and formIssues (and reason on 409); existing fields are unchanged.
  5. Several instances: see Several instances.

Installation

Requirements

  • Rust, stable 1.94 or newer, from rustup.rs. Your application is a Rust project: Cargo builds it together with RustCMS.
  • A C compiler, for the few dependencies with C code (SQLite, TLS):
    • macOS: Xcode Command Line Tools (xcode-select --install);
    • Linux: build-essential on Debian/Ubuntu, gcc or clang elsewhere.
  • macOS or Linux. Windows is not supported: use WSL (Ubuntu), where the Linux build works.
  • Network access to GitHub for the first build: applications depend on RustCMS-Core through a Git tag.
  • A database: SQLite works out of the box; PostgreSQL or MySQL 8.4 for production. Node.js is not needed (the admin panel is built in).

Installing the rustcms command

curl -fsSL https://irisvn.github.io/RustCMS/install.sh | sh

The script picks the build for your system from the releases, checks it against the release’s SHA256SUMS, and installs it in ~/.rustcms/bin. It prints the line to add to your shell profile, or adds it with sh -s -- --modify-path. rustcms self-update updates it later; rustcms doctor checks that this machine can build an application (Rust version, C compiler, access to RustCMS-Core) and says what to install; rustcms docs opens this guide for your version, offline.

  • A given version: RUSTCMS_VERSION=v0.4.0 (release candidates are only installed this way). Another directory: RUSTCMS_INSTALL=/opt/rustcms.
  • To read the script first: curl -fsSLO https://irisvn.github.io/RustCMS/install.sh, then sh install.sh. Or download an archive from the releases page and put rustcms on your PATH yourself.
  • The checksum detects a corrupted download; it does not prove who published the release. Releases are not code-signed yet: an archive downloaded with a browser may be blocked by macOS (xattr -d com.apple.quarantine rustcms). The install script is not affected.
  • Built for macOS on Apple silicon (11 or newer) and Linux (x86_64 and arm64, any distribution: the binary is static). On an Intel Mac, build it from source with Cargo (below).
  • Without the script, Cargo can build it from source: cargo install --git https://github.com/irisvn/RustCMS-Core --tag v0.4.0 rustcms-cli.

Creating an application

rustcms new blog
cd blog
rustcms migrate                    # SQLite file by default (DATABASE_URL in .env)
rustcms make:user --email you@example.com --name You --super-admin
rustcms serve                      # http://localhost:8000/admin

rustcms new writes a project whose Cargo.toml depends on the RustCMS-Core tag of the command’s version, then resolves the dependencies (Cargo.lock):

rustcms = { git = "https://github.com/irisvn/RustCMS-Core", tag = "v0.4.0" }

Commit Cargo.lock: it pins the exact commit and every dependency, so your team and your CI build what you tested (the generated .github/workflows/ci.yml runs cargo test --locked). Offline, rustcms new blog --no-fetch skips the resolution; Cargo does it on the first build. A tag that does not exist, or dependencies that do not resolve, fail the command (the project is left in place to inspect). The first build compiles everything and takes a few minutes; later builds only compile your code.

rustcms new writes a fresh APP_KEY to .env. Never commit .env.

Open http://localhost:8000/admin and sign in. Use the host of APP_URL: sign-in and every change are only accepted from that origin (opening http://127.0.0.1:8000/admin shows the page but sign-in answers 403; list other origins in auth.admin_origins).

Inside an application, rustcms <command> runs your application’s binary (cargo run -- <command>), so your own commands are available too. The command’s own names (new, make:*, doctor, upgrade, self-update, docs) come first; rustcms -- <command> always reaches the application. Once built, the binary takes the same commands: ./blog migrate, ./blog serve.

Your first resource

rustcms make:model Post -m                 # src/models/post.rs + a create_posts_table migration
# edit the model and the migration, then:
rustcms migrate
rustcms make:resource Post --generate      # src/admin/resources/post_resource.rs: fields, form, table
rustcms permission:sync                    # declares posts.view_any, posts.create, …
rustcms serve

Posts now appear in the panel for super admins. Give other users access with roles (System → Roles).

Configuration

Configuration is read when the application starts. Sources, last one wins:

  1. built-in defaults,
  2. config/<section>.toml — each file becomes the section named after it,
  3. well-known variables: APP_NAME, APP_ENV, APP_DEBUG, APP_URL, APP_KEY, DATABASE_URL,
  4. RUSTCMS_<SECTION>__<KEY>, e.g. RUSTCMS_HTTP__BODY_LIMIT=2097152.

.env is loaded first and never overrides variables already set in the environment.

Environment variables

Every key can be set from the environment as RUSTCMS_<SECTION>__<KEY> (nested keys with more __): RUSTCMS_APP__LISTEN=0.0.0.0:8000, RUSTCMS_AUTH__JWT__ACCESS_TTL_SECS=600. Lists are written in TOML syntax: RUSTCMS_HTTP__TRUSTED_PROXIES='["10.0.0.0/8"]'. With every value in the environment, the config/ directory is optional.

From files (Docker and Kubernetes secrets)

Any of these variables (the well-known ones and every RUSTCMS_…) can be read from a file instead: add _FILE to its name and give the path.

APP_KEY_FILE=/run/secrets/app_key
DATABASE_URL_FILE=/run/secrets/database_url
RUSTCMS_MAIL__SMTP__PASSWORD_FILE=/run/secrets/smtp_password
  • The value takes its variable’s place in the order above: a RUSTCMS_DATABASE__URL still wins over DATABASE_URL_FILE.
  • One trailing line break is removed (as echo and editors add it); any other whitespace is kept. Values are read like environment values (true, numbers), except that a value with leading or trailing spaces stays exactly that string.
  • Boot fails when a variable and its _FILE are both set, or when the file is missing, unreadable, empty, not UTF-8 or larger than 64 KiB. The message names the variable and the path, never the content.
  • A key whose own name ends in _file cannot be set from the environment (RUSTCMS_X__LOG_FILE means the file of x.log); put it in a TOML file. A key named file itself is fine: RUSTCMS_LOG__FILE is log.file.

Directory structure

A rustcms application is one Cargo package laid out like a Laravel application: the same folder names, inside src/ (Rust modules live there). rustcms new blog creates:

blog/
├── Cargo.toml / Cargo.lock      # dependencies (≈ composer.json / composer.lock)
├── .env, .env.example           # secrets and per-machine values (.env is git-ignored)
├── config/                      # app.toml, auth.toml, http.toml, log.toml
├── lang/vi.toml                 # translations of your admin labels and messages
├── resources/                   # views/admin (page templates), admin/{js,css} (extensions), logo

Generators

Generators write one file and register it at a // rustcms:… anchor comment (rustcms:resources, rustcms:jobs, rustcms:seeders, rustcms:mods, …). They check every file and anchor first and write nothing if one is missing, or if the file already exists. A folder created on demand gets its mod.rs and a pub mod line in its parent; a flat src/services.rs next to it, or a folder its parent does not declare, is refused. Names that would make a Rust keyword (make:command type), a second DatabaseSeeder or a settings group longer than 32 characters are refused too.

Applications created before 0.3 (src/app.rs, src/migrations/, src/http/api/) are refused until moved: see the upgrade guide.

Where code goes

  • A rule that must hold whoever writes (a course’s seats, a stock level): a service function taking the transaction, called by admin hooks, API handlers, jobs and seeders alike. See the LMS example.
  • Who may see or change a record: a policy, plus the resource’s scope().
  • What a query filter means (published posts, courses someone teaches): a function next to the model, used by scopes and services.
  • Values admins change at run time: a settings group (src/settings/) with its page (src/admin/pages/); values that need a deploy go in config/.

See also Routing, Database and Testing.

Upgrading

  1. Build the new binary and copy it next to the old one (blog.new).
  2. Back up the database (and storage/app on the local disk).
  3. ./blog.new migrate, then ./blog.new permission:sync.
  4. Replace the binary and restart the service.
  5. Check /health and sign in.

To go back, roll back with the new binary first (only it knows its migrations): ./blog.new migrate:rollback --step N, then start the old one. Migrations that drop data cannot restore it: use the backup.

Request lifecycle

Starting

main.rs hands your build function to the console. For serve:

  1. configuration is loaded (config/*.toml, .env, environment);
  2. build(config) assembles the AppBuilder: every provider’s register runs, binding services, routes and commands;
  3. the database is connected (and, for MySQL, its settings checked);
  4. every provider’s boot runs (background jobs start here);
  5. the HTTP server listens on app.listen.

Your own commands, and most framework commands, follow the same steps and run instead of serving. A few do less: key:generate runs before the configuration is complete, the migrate commands only connect to the database, and route:list assembles the application without connecting or booting it.

The HTTP stack

Every request goes through, outermost first:

  1. Request id — x-request-id is generated (UUID) or kept from the request, and returned.
  2. Tracing — one span per request with method, path and request id.
  3. Client IP — the ClientIp extractor; see proxies.
  4. Timeout — http.timeout_secs, then 408.
  5. Body limit — http.body_limit, then 413, on every request body (a larger Content-Length is refused before the handler runs; chunked bodies stop at the limit). Routes may raise it (app.body_limit(method, path, bytes)).
  6. Guard — chosen by path: the admin session guard under auth.admin_path, the API guard elsewhere (Authentication).
  7. Route access — for API routes, the Access you declared, before any extractor reads the request.
  8. Your handler — extractors, then your code.

Unknown routes answer 404 and wrong methods 405, both as JSON. GET /health returns {"status":"ok","database":"ok"}, or 503 when the database is down.

Responses and errors

Handlers return AppResult<T>. Errors become JSON in one format (Errors); internal details are logged, never returned.

Client IP and proxies

X-Forwarded-For is ignored unless the TCP peer is in http.trusted_proxies. Then the client is the right-most address that is not a trusted proxy, so a client cannot choose its address by sending the header itself.

# config/http.toml
trusted_proxies = ["10.0.0.0/8"]

Writing a provider

Routing

Your JSON API is laid out as in Laravel:

src/routes/api.rs                        routes(): every API route and its access
src/http/controllers/post_controller.rs  index, show, store, …
src/http/requests/post_request.rs        NewPost + Validate   (≈ form request)
src/http/resources/post_resource.rs      PostJson             (≈ API resource)

rustcms make:api Post writes the controller (index, newest first when the model has created_at, else highest key first, and show), the JSON resource, and their two routes in src/routes/api.rs. The JSON resource follows the wire format: 64-bit integers, UUIDs and dates as strings, decimals at their declared scale, instants in UTC with Z; secret-looking columns (password, token, …) are left out.

Declaring routes

// src/routes/api.rs
use crate::http::controllers::post_controller;

    ApiRoutes::new("/api/v1")

        .get("/posts", Access::can("posts.view_any"), post_controller::index)

        .get("/posts/{id}", Access::can("posts.view_any"), post_controller::show)
        // rustcms:api-routes
}

Access

Every route states its access; there is no default:

AccessAllows
Access::public()anyone
Access::authenticated()any valid API token or JWT
Access::can("posts.create")a caller whose user holds the permission (and whose token abilities allow it)

Access is checked before the handler runs, so before any extractor reads the request: without the permission a client gets 403 whatever its body, path or query (only the global body limit, 413, comes first). Do not authorize inside a handler after reading the body.

  • Admin-panel sessions are not API credentials (401).
  • An invalid bearer token is 401 everywhere, public routes included.
  • HEAD follows GET; other methods of a path answer 405.
  • No API route may match a path under auth.admin_path, captures included (/{section}/report is refused with the default /admin): registration panics. Endpoints for the panel’s own pages, on its session, are admin routes.

api_permissions declares each Access::can permission on the API guard, in the group named before the first . (posts.create → posts). A permission you declare yourself with .permission(API_GUARD, …, group) keeps your group. Run rustcms permission:sync after adding routes.

Validating input

Validated<T> reads the JSON body, then calls T::validate:

    pub title: String,

impl Validate for NewPost {
    fn validate(&mut self) -> Result<(), ValidationErrors> {

Database & migrations

RustCMS uses SeaORM 2.0. SQLite, PostgreSQL and MySQL 8.4 are supported (MariaDB is not). Configure the connection with DATABASE_URL (Configuration).

Models

Models are SeaORM entities in src/models/. rustcms make:model Post -m writes the entity and a migration creating its table:

#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel)]
#[sea_orm(table_name = "posts")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i64,
    pub title: String,
    pub published_at: Option<DateTimeUtc>,
    pub created_at: DateTimeUtc,
}

Query them with SeaORM, using the pool from the state:

let posts = post::Entity::find().filter(post::Column::Title.contains("rust")).all(app.db()).await?;

The framework’s own tables (users, sessions, roles and permissions, media, …) come with the framework’s migrations, which run before yours. rustcms::models::user is the users entity.

  • SQLite connections always enable foreign keys, WAL and a 5s busy timeout.
  • MySQL connections always use UTC and the utf8mb4_0900_bin collation; write transactions run in READ COMMITTED, as on PostgreSQL. See MySQL for the database settings rustcms checks at startup.

MySQL

Create the database with the collation rustcms needs, so text compares as on PostgreSQL (case, accents and trailing spaces all count):

CREATE DATABASE app CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_bin;

serve, the migrate commands and the app builder refuse to start when the database, any string column or the engine of any table differs (every table InnoDB), when sql_mode (global or session) is not strict or has NO_BACKSLASH_ESCAPES, or when the connection is not in UTC with that collation (pools opened with rustcms::db::connect always are). The error lists the SQL that fixes it.

Differences to know:

  • DDL is not transactional: each statement commits. A migration that fails half-way is retried on a partly changed schema. Use the helpers below, which skip what exists, and stop writers while migrating.
  • Column types: a bare String field is varchar(255) (PostgreSQL: unbounded); Text holds 64 KiB. JSON columns accept no literal default (only an expression default such as ('[]')).
  • Sort order of text is binary (code points), not a locale.
  • Instants are DATETIME(6) in UTC (MySQL’s TIMESTAMP stops in 2038 and drops fractions); fractions below a microsecond are truncated.

Migrations

src/database/migrations/mod.rs runs the framework migrations and then yours (one file per change, rustcms make:migration <name>):

CommandDoes
rustcms migrateapply pending migrations
rustcms migrate:statuslist applied / pending
rustcms migrate:rollback --step Nundo the last N

Framework and generated migrations run in a transaction on every backend (use_transaction() -> Some(true)), including SQLite whose default is none: a failed migration leaves no partial schema and can simply be retried. On MySQL each DDL statement also commits what the migration wrote before it, so a failed migration can leave both schema changes and data behind: write migrations that can run again (see above). Keep Some(true) in your own migrations unless a statement cannot run in a transaction.

Never edit a migration that has run in production; add a new one. A migration that cannot be reversed must say so in its down and in its doc comment.

Testing

rustcms-testing gives each test its own database and drives the full router (middleware included) without opening a socket.

Feature tests live in tests/feature/, one module per file, compiled as one test binary (tests/feature/main.rs lists them; cargo test --test feature runs them alone). Helpers shared by suites go in tests/support/mod.rs, included with #[path = "../support/mod.rs"] mod support;. rustcms make:test PostAdminTest writes tests/feature/post_admin_test.rs and adds it to main.rs.

use blog::bootstrap;
use blog::database::migrations::Migrator;
use rustcms_testing::{TestApp, TestDb, UserFactory, Factory, db_test};

db_test!(lists_posts, migrate = Migrator, |db: TestDb| async move {
    let app = TestApp::new(bootstrap::build, db).await;
    let user = UserFactory::new().create(app.state().db()).await;
    // Without credentials the route is closed; with a token holding the permission it answers.
    app.get("/api/v1/posts").await.assert_status(StatusCode::UNAUTHORIZED);

db_test! generates three tests, …::sqlite, …::postgres and …::mysql.

Databases

  • SQLite: a temp file per test, opened with production options (foreign keys, WAL), so locking behaves like the real thing.

  • PostgreSQL: set RUSTCMS_TEST_PG to an admin URL, e.g. postgres://postgres:postgres@localhost:55439/postgres. Each test gets its own database. With migrate = M, the migrated schema is built once as a template database and cloned per test. After editing an unreleased migration in place, drop the template databases (named rustcms_tpl_…): the template is keyed by the migration names, not their contents.

  • MySQL: set RUSTCMS_TEST_MYSQL to an admin URL, e.g. mysql://root:mysql@localhost:53306/mysql. Each test gets its own database (utf8mb4_0900_bin); with migrate = M, a migrated template is built once and its tables (with their foreign keys) and rows are copied per test.

  • Tables built from entities (Schema::create_table_from_entity) go through rustcms_testing::create_table, which gives MySQL the same instants as migrations (DATETIME(6)). Without migrate = M, also create the audit_logs table (rustcms::models::audit_log::Entity): resource writes record into it.

  • S3: rustcms_testing::TestS3::from_env() reads RUSTCMS_TEST_S3 (http://host:port/bucket, e.g. S3Mock: docker run -p 59000:9090 -e COM_ADOBE_TESTING_S3MOCK_STORE_INITIAL_BUCKETS=test adobe/s3mock:5.2.3) and TestS3::configure(config) points [storage] at it.

Without RUSTCMS_TEST_PG / RUSTCMS_TEST_MYSQL, those variants print a skip notice and pass, unless RUSTCMS_TEST_REQUIRE lists them (postgres,mysql): then they fail. Set them in CI so every test runs on the three databases.

While working, just test-fast in RustCMS (or RUSTCMS_TEST_BACKENDS=sqlite cargo test in an application) runs every test on SQLite in seconds; run every database before pushing. Test servers are faster in memory and without fsync (RustCMS’s docker-compose.yml does it: PostgreSQL -c fsync=off -c synchronous_commit=off -c full_page_writes=off, MySQL --innodb-flush-log-at-trx-commit=0 --innodb-doublewrite=OFF --innodb-flush-method=nosync --sync-binlog=0 --skip-log-bin, data dirs on tmpfs); never use these settings for data you keep.

An application that runs on one database can test only that one: RUSTCMS_TEST_BACKENDS=mysql (any of sqlite,postgres,mysql) runs those variants and makes them required, so a missing server fails instead of skipping. An empty or unknown name fails, as does a backend that RUSTCMS_TEST_REQUIRE asks for but the selection leaves out. Unset, all three run as before.

Authentication

AuthProvider (registered by rustcms new) adds two guards, chosen by path:

A credential that is present but invalid is a 401: there is no fallback to another driver. An admin cookie never authenticates API routes, and a bearer token never authenticates admin routes.

For API routes, state the access on the route (ApiRoutes, see Routing): it is checked before the request body is read. In a handler, Auth gives the user and its permissions:

use rustcms::prelude::*;

// Routed with `.post("/", Access::can("posts.create"), create_post)`.
async fn create_post(auth: Auth, Validated(input): Validated<NewPost>) -> AppResult<StatusCode> {
    // auth.0.user is the user record, auth.principal() the permissions
    Ok(StatusCode::CREATED)
}

Checking a permission inside a handler (auth.authorize(…)) runs after the handler’s extractors, so after the body was read: prefer route access.

Admin sessions

  • The cookie (rustcms_session, HttpOnly, SameSite=Lax, Path=<admin_path>, Secure when APP_URL is https) holds 43 random characters. The database stores only their HMAC-SHA256 keyed with APP_KEY: rotating the key (key:generate --force) signs every admin out (API tokens are kept).
  • The cookie has no Max-Age: it lasts until the browser closes, and expiry is enforced by the server. Remember me (the sign-in page’s box, remember in POST auth/login, shown while remember_days > 0) gives the cookie a Max-Age of remember_days (30) from sign-in and the session that idle lifetime; every revocation below still ends it at once. It is sent only when its value changes (sign-in, re-issue, sign-out), so a slow response can never restore a replaced cookie.
  • The session id is regenerated at sign-in and whenever credentials change.
  • Sessions expire after session_lifetime_minutes of inactivity; serve deletes expired rows hourly (session:prune does it on demand; idempotency:prune does the same for idempotency receipts).
  • Anonymous sessions (a CSRF token before sign-in) live a fixed anonymous_session_lifetime_minutes (15): activity never extends them. Creating one is throttled per IP (anonymous_sessions_per_ip, 30/min) and globally (anonymous_sessions_per_minute, 1,000/min), so at most 1,000 × 15 anonymous rows are alive; an existing session can always fetch its token again.
  • Sliding renewal is best effort: if writing it fails, the response the handler produced (possibly after committing changes) is returned unchanged.
  • A credential change (password, sign-out everywhere) re-issues the session within its lineage (the first session of the chain), only if it still exists. Signing out ends the whole lineage. Both take a per-lineage lock first, so a sign-out and concurrent re-issues — however many — never leave a live session, in any order. Signing in starts a new lineage.
  • Every request reloads the user: a disabled user, or one whose auth_version changed, is signed out immediately.
  • If another request ends the session while one is in flight, the in-flight response is kept and the session stays ended (it is never re-created).

Password resets and invitations

Forgot password? With auth.password_reset = true (boot fails without a mail driver), the sign-in page links to <admin>/forgot-password:

  1. POST auth/forgot-password {email} always answers 202 {} — for an account, an unknown address, a disabled or invited one — after the same single insert (a queued job), so neither the answer nor its timing tells which. Throttled per IP (reset_requests_per_ip, 5/min), per address (reset_requests_per_email, 3/min) and in total.
  2. The job (auth.password_reset) finds the account, makes the token under the user’s row lock and mails the link at once: the token never sits in the queue. A request older than 15 minutes sends nothing; a newer request replaces the link of an older one; a second request within reset_cooldown_secs (60) sends nothing (a retry of the same request does).
  3. The link is <APP_URL><admin>/reset-password#token=<id>.<secret>: the secret is in the fragment, which browsers never send to the server nor put in a Referer; the page reads it, removes it from the address bar, and is served with Referrer-Policy: no-referrer.
  4. POST auth/reset-password {token, password, password_confirmation}: the password rules first, then the token (one answer, token: is invalid or has expired, whatever is wrong). Under the user’s lock then the token’s, everything is checked again — the secret, its purpose, expiry (password_reset_minutes, 60), the same email and credential version, the account enabled — and the new password, the end of every token of the user and the revocation of their sessions (and API tokens with revoke_tokens_on_password_change) commit together. 204: sign in with it.

Only an HMAC of the secret is stored (keyed from APP_KEY: rotating the key kills every link). At most one link lives per user and purpose; any credential change (password, email, disabled, signed out everywhere) kills it. serve deletes expired tokens hourly.

Invitations (see Users) use the same machinery: <admin>/invitation#token=…, POST auth/invitation {token, password, password_confirmation, name?}, valid invitation_days (7, at most 30). Once a link is used, or an administrator sets the password, any older request still waiting in the queue sends nothing. An invited user cannot sign in until they accept (no password matches theirs), and does not count as the “last active super admin”.

API tokens

How clients obtain and use tokens is in API authentication. POST /api/v1/auth/token with {email, password, token_name, abilities?, expires_in_days?} returns the token once. DELETE /api/v1/auth/token revokes the current one; GET /api/v1/auth/me describes it. Operators use rustcms token:create.

A token acts with the intersection of its abilities and the user’s permissions in the api guard. ["*"] means all of the user’s permissions. Even a super admin’s token is limited to its abilities.

JWT sign-ins

POST /api/v1/auth/jwt with {email, password, abilities?} (same limits as sign-in, plus 20 sign-ins per user per minute) returns an access token (a JWT, auth.jwt.access_ttl_secs, default 15 minutes) and a refresh token. POST /api/v1/auth/refresh {refreshToken} returns the next pair; each refresh token works once: using a spent one again (a replay, two tabs racing, or a retry after a lost response) ends the whole sign-in, so clients must refresh one at a time and keep the newest token. POST /api/v1/auth/jwt/logout {refreshToken} ends the sign-in (also after the access token expired). Refresh and logout are limited per IP (60/min) and per sign-in (30/min).

Access tokens are HS256 with a key derived from APP_KEY (rotating it ends every sign-in); only that exact header is accepted. Each request still checks the user (active, same auth_version) and the sign-in (not ended), so revocation applies from the next request, as for sessions. Abilities are fixed per sign-in and narrow the user’s API permissions like a token’s.

Throttling

Sign-in attempts (admin login and token issuance) are limited per account+IP (attempts_per_identifier, default 5/min) and per IP (attempts_per_ip, 30/min); then 429 with Retry-After. Each attempt is counted before the password is verified, so a burst of concurrent guesses cannot exceed the limit, and a request cancelled mid-check stays counted; a successful sign-in clears the account counter and refunds the IP. The IP comes from the trusted-proxy rules. Unknown emails cost the same Argon2 time as wrong passwords and return the same message.

Emails longer than 255 characters and passwords longer than 1024 are rejected before any throttling state or hash is built. Throttling keys are stored as fixed-size hashes; expired windows are reclaimed and the table is capped (100,000 keys, oldest dropped first), so unauthenticated traffic cannot grow memory without bound.

Limits are kept in memory, per instance; with Redis ([redis] url, feature redis) every instance counts in Redis, atomically across all the keys of one check. If Redis does not answer, checks fail closed (500). See Several instances.

Roles & permissions

Permissions decide what a user may do; policies decide it per record in the admin panel, and route access per API route.

Spatie-style tables, scoped by guard: permissions, roles, role_has_permissions, model_has_roles, model_has_permissions (columns, keys and how they relate: Database schema). A user may hold roles in both guards; they never mix.

  • Deny by default. Missing permission → 403.
  • Super admin. The system role super_admin (seeded per guard by the migrations) passes every check in its guard, still bounded by token abilities.
  • Gate. Ad-hoc abilities: AuthProvider::new().define("publish", |p| …), checked with gate.allows(principal, "publish").
  • Declaring permissions. AuthProvider::new().permission("api", "posts.view", "posts"), then rustcms permission:sync. Sync never renames or deletes: undeclared permissions become orphaned and stop granting access.

Changing access: RbacService

Every change goes through RbacService, with Actor::User(&principal) for people and Actor::System for trusted operators (console). It refuses:

Every change runs in one transaction that first takes the RBAC lock (rbac::lock: a transaction-scoped advisory lock on PostgreSQL, the write lock on SQLite) and then re-reads the actor’s own grants. Concurrent changes are therefore applied one after another, each checked against the state left by the previous one: an edit cannot restore a permission revoked meanwhile, and a promotion racing a removal cannot leave a guard without an active super admin.

Each change that changes something is recorded in the audit log, in the same transaction, with the actor. To record the request too (IP, user agent, request id), pass the context: RbacService::new(db, &auth.resolver).audited(AuditContext::new(AuditActor::user(&principal), request)).

Creating roles from code

The panel manages admin-guard roles. API-guard roles (for tokens and JWT), or roles you seed, are created through RbacService, for example in a console command:

use rustcms::auth::{API_GUARD, Actor, AuthState, RbacService};

async fn run(&self, state: &AppState, _: &ArgMatches) -> anyhow::Result<()> {
    let auth = state.service::<AuthState>().expect("AuthProvider");
    let rbac = RbacService::new(state.db(), &auth.resolver);
    rbac.sync_permissions(&auth.permissions.all()).await?;          // the declared permissions exist
    let permissions = ["posts.view_any".to_owned(), "posts.create".to_owned()];
    let role = rbac.create_role(Actor::System, API_GUARD, "publisher", &permissions).await?;
    println!("created role {}", role.id);
    Ok(())
}

Then assign it: rustcms role:assign --email bot@example.com --role publisher --guard api, and issue a token with rustcms token:create.

Mechanism: account changes bump users.auth_version in the same transaction; sessions and JWT sign-ins store the version they were issued for and are checked on every request (an access token also checks that its sign-in is not revoked or expired). revoke_tokens_on_password_change applies to API tokens only: JWT sign-ins behave like sessions. Races

  • Password changes, sign-out everywhere and token issuance re-check, inside a write transaction holding the user row, that the credentials verified earlier in the request are unchanged (password hash, auth_version, active). A token obtained with a password that is changed concurrently is refused, never issued after the revocation.
  • The permission cache is keyed by a generation advanced on every RBAC change: a lookup that started before a change cannot repopulate the cache with the old permissions.
  • JWT refresh tokens rotate under the locks of the user, the sign-in and the token, in that order (the same order as issuance and revocation). Two refreshes with one token: one wins, the other counts as a replay and ends the sign-in.
  • A request whose session was revoked can start a new one (CSRF, sign-in) in the same response.

Production checklist

  • APP_ENV=production, APP_DEBUG=false.
  • APP_KEY generated once (key:generate), stored as a secret, never committed. Rotating it signs every admin out, ends every JWT sign-in (API tokens stay valid) and makes secret settings unreadable until they are entered again.
  • APP_URL is the public https URL (enables Secure cookies and the default allowed origin).
  • auth.admin_origins lists every origin serving the admin panel, nothing else.
  • http.trusted_proxies lists only your load balancers, so throttling sees real client IPs.
  • Several instances: build with the redis feature and set [redis] url (one standalone Redis, one redis.prefix per deployment) so rate limits are shared and periodic jobs mostly run on one instance (best effort: jobs are safe to run twice, also at the same time); the permission cache needs nothing (it follows the database). Media storage must be shared (S3, or one volume mounted by every instance). Without Redis, run one instance.
  • S3 storage: a private bucket, credentials limited to it, an abort incomplete multipart uploads lifecycle rule, storage.root writable by the app only (uploads are staged there), media:prune scheduled (File storage).
  • Password-hashing and upload concurrency limits are per instance (each bounds its own CPU and disk).
  • Queue workers: decide where they run (serve, or queue:work processes with queue.enabled = false on web instances); clocks synchronized (NTP); queue:failed watched; job payloads and error messages carry no secrets (Queues); queue.manage (retry, forget, cancel jobs) only for operators.
  • First super admin created with make:user --super-admin; permission:sync run after each deploy.
  • TLS terminates before the app; HTTP redirects to HTTPS at the proxy.
  • WebSocket routes (realtime): the proxy passes Upgrade and allows long-lived connections, and its access and APM logs drop the Sec-WebSocket-Protocol request header (it carries the session’s CSRF token).
  • Database backups include sessions only if you want sessions to survive restores.
  • audit.retention_days set to what you must keep, no longer: the audit log holds personal data (IP addresses, emails typed in failed sign-ins), and so do backups that include it. Restrict who can read audit_logs; ship it elsewhere if it must be tamper-proof.

Security

  • Content Security Policy default-src 'self', script-src 'self', style-src 'self', frame-ancestors 'none', plus X-Frame-Options: DENY, nosniff and Referrer-Policy: same-origin. Extensions must follow it (no inline scripts or styles).

  • Signing out (or a 401, or signing out in another tab) clears every cached record, schema and form. Panel API responses are private, no-store.
  • After sign-in the user returns to the page they asked for, never outside the panel.

Hooks

Hooks are async methods of the resource (use rustcms::async_trait; and put #[async_trait] on the impl; an attribute path cannot start with rustc…). Every write runs in one transaction:

  1. reject undeclared or non-writable keys (422),
  2. type-check values against the wire format,
  3. check relationship keys against the target scope,
  4. mutate_before_create / mutate_before_update hooks,
  5. re-check limits (max_length) on the final values, so hooks cannot bypass them,
  6. write (database constraints are mapped to field errors with ResourceMeta::unique),
  7. after_save hook — an error rolls everything back.
async fn mutate_before_create(ctx: &Ctx, _txn: &DatabaseTransaction, mut data: Data) -> AppResult<Data> {
    data.insert("author_id".into(), json!(ctx.principal.id));     // guarded fields may be set here
    Ok(data)
}

async fn after_save(ctx: &Ctx, txn: &DatabaseTransaction, post: &post::Model) -> AppResult<()> {
    // runs in the write's transaction: an error rolls everything back
    Ok(())
}

mutate_before_update receives the current record too; after_force_delete runs when a trashed record is deleted for good. A message a hook returns is shown as written: translate it with ctx.t("…") (i18n).

Parent locks

A rule over a parent’s children (at most capacity active enrollments per course) or a permission read through the parent (the course’s instructor) holds only if writes under one parent do not interleave. Declare the parent:

fn meta() -> ResourceMeta {
    ResourceMeta::new("Enrollment").lock_parent("course_id", "courses")
}

Every write to an enrollment (create, update, delete, restore, force delete, actions, creates from a course’s page) then locks its course row before the enrollment, and both courses when it moves. Hooks run under that lock, so a count in mutate_before_create is exact, and an instructor removed from the course meanwhile no longer passes the scope, checked again under the lock.

  • One order everywhere: parent, then child, the order a parent’s deletion cascades in, so writes and deletions never deadlock. A write takes at most one xact_lock and takes it first; parent locks come after it.
  • The field must be a belongs_to the target; one parent per resource, and the parent may not lock a parent of its own (checked at boot).
  • A hook, an action or a column default that puts a record under a parent that was not locked fails (500, nothing written): send the parent field (make it .required()), and change it through an update. A record moved by someone else between reading and locking answers 409 write_conflict; send the request again.
  • Writes under one parent wait for each other; writes under different parents do not. SQLite runs one writer at a time anyway.

Soft deletes

fn meta() -> ResourceMeta {
    ResourceMeta::new("Post").soft_deletes()   // or .soft_deletes_column("removed_at")
}

The marker is a nullable timestamp column (Option<DateTimeUtc> or Option<DateTime>), declared as a field only if .guarded() (e.g. .guarded().readable(|_| true) to show it); hooks may not write it.

  • Delete sets the marker. Trashed records disappear everywhere: lists, reads, writes, actions, relationship options and labels (#key), and references from other records (422). No database cascade runs: related records are kept.
  • Restore ({slug}.restore) clears the marker. The record’s relationships must still point to records the user can see (422 otherwise); after_save runs.
  • Force delete ({slug}.force_delete) removes a trashed record for good; database foreign-key actions apply then.
  • The trash (trashed=with|only) needs restore or force_delete, and shows a record only if the policy allows view and one of them on it. With a custom policy, override admits for these abilities like the others.
  • Unique values stay taken by trashed records (the database still holds them).
  • make:resource --generate adds .soft_deletes() for a nullable deleted_at timestamp.

Actions

Actions run on one record (row actions) or on the selected records (bulk actions), with the same authorization as any write.

fn actions() -> Vec<Action<post::Entity>> {
    vec![Action::<post::Entity>::new("publish", |_ctx, txn, posts, _data| {
        Box::pin(async move {
            for post in posts {
                let mut post = post.into_active_model();
                post.published = Set(true);
                post.update(txn).await?;
            }
            Ok(())
        })
    })
    .label("Publish")
    .bulk()
    .requires_confirmation("Publish the selected posts?")]
}

Name the entity (Action::<post::Entity>::new) so the closure’s types are inferred. Each selected record is checked by the policy with the action’s ability (default: its name, or .ability("update")); denied records are reported, not processed, and envelopes tell the client per record. Add .requires_permission("posts.publish") to refuse the action outright (403, and hidden from the schema) for users without that permission.

Authorization

The admin panel is deny by default. Every request, from the panel or any other client, is checked on the server; what the panel hides is never what protects your data.

Rules

  • Deny by default. Without a custom policy, every ability requires the permission {slug}.{ability} (posts.update).
  • Columns not declared as fields are never read or written by clients.
  • Field rules (readable, creatable, updatable) are evaluated on the server for every request. Client-side visibility never grants write access.
  • guarded() fields are never written from input; hooks may set them.
  • Lists never show records the policy denies view. With a record-dependent policy (the default for custom policies), lists check each matching record and count only visible ones (up to 10,000 matching rows, then 422). Put large visibility rules in scope() and return false from Policy::view_depends_on_record to keep SQL pagination.
  • scope() restricts which records exist for the user. It applies to lists, lookups, writes, actions and relationship options and labels — and to the response of a write: a record the write moved out of the user’s scope comes back as its key only.
  • No existence probing. Requests by key (find, schema of a record, update, delete, actions, options of a record) first ask Policy::admits(ctx, ability); refused, they answer 403 whether or not the key exists. The default policy admits holders of {slug}.{ability}. Custom policies admit everyone by default (then a missing key is 404 and a denied record 403): override admits when an ability needs a permission regardless of the record.
  • Relationships: a belongs_to key sent by a client must be visible to that user in the target resource, otherwise the request fails with 422.

Policies

Without a policy, every ability requires the permission {slug}.{ability}. A custom policy decides per record:

use rustcms::async_trait;

pub struct PostPolicy;

#[async_trait]
impl Policy for PostPolicy {
    async fn allows(&self, ctx: &Ctx, ability: &str, record: Option<&Data>) -> bool {
        let own = record.and_then(|r| r.get("author_id")) == Some(&json!(ctx.principal.id));
        match ability {
            "update" | "delete" => ctx.can(&format!("posts.{ability}")) || (own && ctx.can("posts.update_own")),
            other => ctx.can(&format!("posts.{other}")),
        }
    }
}

// in the resource
fn policy() -> Arc<dyn Policy> {
    Arc::new(PostPolicy)
}

rustcms make:policy PostPolicy writes a starting point. Declare extra permissions such as posts.update_own on the AuthProvider (.permission(ADMIN_GUARD, "posts.update_own", "posts")).

Relationships

A resource can list the records of another resource that point to it, on its own view page, and create new ones there: a has-many relation. The child keeps a belongs_to field to the parent.

impl Resource for CategoryResource {
    // …
    fn relations() -> Vec<Relation> {
        vec![Relation::has_many("posts", "posts", "category_id").label("Posts")]
    }
}

impl Resource for PostResource {
    fn fields() -> Vec<Field> {
        vec![
            // …
            Field::column(post::Column::CategoryId).belongs_to("categories"),
        ]
    }
}

Relation::has_many(name, target, field): name is the relation’s id in URLs (snake_case, unique on the resource), target the child resource’s slug and field the child’s foreign key. The registry checks, when the panel starts, that the target exists, that field is a field of it declared belongs_to("<this slug>"), that its column kind matches this resource’s primary key and that it is not the child’s own key; anything else panics with the fix.

What users see

On the parent’s view page, each relation is a section with a compact table of the children: the target’s table columns (without the foreign key), search and paging, and a View link per row. Edits and deletes happen on the child’s own pages. New opens the child’s create form for this parent: the foreign key input is not shown, the server sets it, and the form returns to the parent when saved.

Authorization

Nothing is bypassed: a relation is the target’s own list and create, with one extra condition (field = parent key).

  • Listing needs view on the parent resource (admits) and the target’s view_any, checked before the parent is looked up: without them the answer is 403 whatever the key. Then the parent must be visible to the user (scope, policy, not trashed), otherwise 404, exactly like GET …/records/{key}. The children are filtered by the target’s scope, policy and field rules as on its own list; trashed=with|only works as there. The foreign key field must be readable by the user. Every check that does not depend on a record (the abilities, trashed, the readable foreign key, paging) runs before the parent is looked up, so a refusal never tells whether the parent exists.
  • Creating needs view on the parent resource, the target’s create and write access to the foreign key field on create (all checked before the parent is looked up: 403), then a visible parent (else 404). Like any belongs_to value, the parent must also pass the reference check, which needs the parent resource’s view_any and view. The foreign key is set by the server before the input is validated, so the field must be writable on create by the user and all the usual rules run (belongs_to included, after hooks). A client that sends the foreign key gets a 422 (is set by the relation). If a hook changes it, the write fails (500) and nothing is stored.
  • The parent’s view schema lists only relations whose target the user may list (relations[].create says whether New is offered).

A parent trashed while a child is being created keeps the write-in-progress rule: the child’s belongs_to check sees the parent as it was when the check ran.

Idempotency

Relation creates accept Idempotency-Key like any create. The claim is bound to the relation and the parent: the same key sent to another parent (or to the target’s own create route) is a separate claim, not a replay. A committed retry is answered even if the parent was hidden, trashed or deleted since, like any replay.

  • Attach: choose records of the target (its options: in the user’s scope, allowed to view; already linked ones are marked) and the pivot columns set on new links. Attaching a record already linked keeps that link as it is.
  • Detach: the selected links. Links to records the user cannot see are never touched.
  • Edit link: the pivot columns the user may update.

Permissions

Writes need an ability of the parent record: attach_{relation}, detach_{relation} and update_pivot_{relation} (only with pivot fields). With the default policy that is posts.attach_tags, posts.detach_tags, posts.update_pivot_tags, declared for permission:sync. A policy of your own receives them like any ability; if it decides per record (allows with the record), also override Policy::admits for them, so users without the permission are refused before the request body is read.

Every write checks, in this order: the ability is admitted (403, whatever the body or the record); the body (422: 1 to 100 keys, pivot columns by their field rules; undeclared columns are refused); then, in one transaction, the parent record (in scope: 404; policy: 403) locked, and the targets the user may view locked and checked again. Targets not found, outside the user’s scope, trashed or not viewable come back in missing and are left alone. The answer is {processed, missing}.

Pivot columns are fields: readable, creatable, updatable, required, max_length apply, values follow the wire format; columns not declared never leave the server. Pivot columns not declared must be nullable or have a default; a mandatory one is a .required() pivot field (the panel refuses to start otherwise), and users who may not write it cannot attach (403). Attaching sends only the pivot columns the user filled in (the others keep their database defaults); editing a link sends only what changed, and a change to the values already stored writes and records nothing.

Rules checked at boot

  • The two key columns exist in the pivot with the types of the two keys.
  • One relation per pivot table, and not to the same resource; the target may not declare lock_parent; and no cycle among resources, counting both belongs-to-many (parent before target) and lock_parent (parent before child): posts → tags with tags → posts is refused. These keep one lock order for every writer: the parent (and its own lock_parent), then the targets in key order, then the pivot rows.

The record’s history lists link changes (attached, detached, pivot_updated): which records and the pivot values only to readers who may list the target (pivot values they may read now), otherwise the relation and how many.

Attach and detach send no Idempotency-Key: sending one again gives the same links. If the answer is lost, the panel pauses writes to the resource until the page is reloaded, then shows the links as they are.

Records are linked only from the relation manager for now; a multi-select of links in the record’s own form is not available yet.

Import and export

A resource can be exported as CSV (the list as the user sees it, in a file a spreadsheet opens) and imported from CSV files.

Exporting

fn meta() -> ResourceMeta {
    ResourceMeta::new("Post").title("title").exportable()
}

The list gets an Export CSV button for users who may export (posts.export with the default policy, on top of listing posts: the export ability; the schema’s abilities.export says so).

What a file holds

  • The rows the list shows with the same query: scope, filters, search, sort, trash, and the policy checked on each record (no page: every matching row).
  • The fields the user may read, in the order of fields(); a header of field names. Columns that are not declared never leave the server.
  • Values in the wire format: 64-bit integers and decimals as written, booleans true / false, JSON as its text. An empty cell is null, "" an empty text.
  • Text that a spreadsheet would run as a formula (starting with =, +, -, @, also after spaces, or with a tab or line break) is written with a leading '. Numbers and dates are written as they are. Such a cell keeps its ' if the file is read back elsewhere.

At once or in the background

  • At once (GET {admin}/api/resources/{slug}/export?…, the list’s query string): up to 1,000 rows and 10 MiB. The file is built in full before anything is sent; beyond, 422 (too_many_to_export, too_large_to_export) and the panel offers to export in the background.
  • In the background (POST …/exports?… with no body, needs the storage provider): up to 10,000 rows and 50 MiB, at most three waiting per user, Idempotency-Key honoured (a retry answers with the same export). A job builds the file; the list shows Exports with their state and a Download button. Files are deleted after 24 hours.

A background export is the user’s alone, and stays theirs only while they may see it:

  • The job loads the user again at each batch of 500 rows: a disabled account, changed credentials (password, sign-out everywhere), a withdrawn export permission or a field they may no longer read stops it (failed, with the reason: revoked, account_changed, fields_changed, too_large, unfinished, failed).
  • The fields are fixed when it is asked for: the export fails rather than leaving one out silently.
  • Each run of the job writes its own file; the first run to finish publishes its file together with the list of records in it.
  • Downloading (GET {admin}/api/exports/{id}/file) checks again: same user and credentials, export, the fields, and that every record in the file is one they may still view. Otherwise 409 export_stale: export again. Someone else’s export answers 404, like one that does not exist.

Records found when the job ran are written as they were then; records deleted or hidden while it runs are left out.

Audit

Each export at once and each download records exported on the resource: how many rows and the shape of the query (which fields were filtered, whether there was a search, the sort), never the searched or filtered values.

Importing

fn meta() -> ResourceMeta {
    ResourceMeta::new("Learner").title("name")
        .unique("learners_email_key", &["email"], "is already registered")
        .import_key("email")      // rows naming a known email update it
}

ResourceMeta::importable() (or import_key) adds Import CSV to the list for users with import (learners.import) and create (or update, with an import key). Imports need the storage provider.

  1. Upload (POST {admin}/api/resources/{slug}/imports, the CSV file as the body, text/csv): admitted before the file is read; UTF-8 (a BOM is skipped), at most 5 MiB, 10,000 rows, 100 columns, 10,000 characters per cell, a header of distinct names; at most three imports waiting per user. With an Idempotency-Key header, sending the same file again (the answer was lost) answers with the same import. The answer lists the columns, the fields the user may set (the import key marked) and a suggested mapping (column = field name or label, any case).
  2. Check (POST imports/{id}/preview {mapping}): every row converted and checked as the create (or update) path would before any hook: field rules, types, required fields. Nothing is written and no hook runs, so a row may still fail when it runs (a hook, a unique value, a reference).
  3. Import (POST imports/{id}/run {mapping}): once (a second run answers 409 import_started); the mapping is fixed then. A job writes each row in a transaction of its own through the usual create or update path (field rules, hooks, policy, scope, unique constraints, audit). Each row’s transaction checks the user’s permissions as they are then (a role change waits for it) and records that the row was written: if the job runs again after a crash, rows already written are skipped, and counted as before. An import is kept 24 hours from the time it started; nothing is written after that.
  4. Outcome (GET imports/{id}): created, updated, failed, and the problems of the rows that failed (row, field, a message in the user’s language; never the values of the file, nor a hook’s own message: those show as “is invalid”). Imports are deleted after 24 hours.

Cells are read by the field’s type like query strings (7, true, 2026-10-22); an empty cell is null (an empty text for optional text fields that may not be null), and a quoted empty cell "" of an optional text field the empty text, as exports write them (a required field is never set empty: the row is refused). With an import key, a row whose key cell is filled updates the record of the user’s scope with that value (the key itself is not written), creates one when there is none, and fails when several match; a row without a key value is created. A trashed record with the same key is not matched (the unique constraint then refuses the row).

The job loads the user again at each batch of 100 rows (active, same credentials, import still allowed); otherwise it stops (revoked, account_changed). Each row’s write checks the user’s permissions as any write does. An imported audit entry records the counts; each record created or updated has its own entry as usual.

Media, uploads & rich text

The media library stores uploaded files and lets records reference them; rich text fields hold documents that may embed images from it.

Enabling

app.provider(rustcms::storage::StorageProvider);          // `[storage]`
app.provider(AdminProvider::new().media().resource::<PostResource>());

media() adds the Media resource (permissions media.view_any, media.view, media.create, media.delete, media.restore, media.force_delete, media.manage_all), the upload route and media:prune.

Files are kept on the configured storage (local disk or S3-compatible).

Uploads

POST {admin}/api/media, multipart/form-data with exactly one part named file. It needs media.create, CSRF and an allowed Origin, and may carry an Idempotency-Key.

  • The type is detected from the content (magic bytes), never from the name or the declared type. SVG, HTML, XML and scripts are never accepted.
  • Images must be readable (dimensions within max_pixels).
  • Answer: 201 {data: {id, name, mime, size, width?, height?, inline}}. Storage paths are never sent.
  • An upload is recorded before its file is stored and committed with its row; a crash in between is cleaned by media:prune (also run every minute by serve).

Downloads

GET {admin}/api/media/{id}/file serves the bytes through the application (no presigned URLs) to users who may view the media record (scope: own uploads unless media.manage_all). Trashed media is not served. Headers: X-Content-Type-Options: nosniff, Content-Security-Policy: sandbox; default-src 'none', Cache-Control: private, no-store, and Content-Disposition: inline for png/jpeg/gif/webp, attachment otherwise.

Deleting media for good queues its file’s removal in the same transaction; the worker retries until it succeeds.

Media fields

Field::column(post::Column::Cover).media().accept(&["image/*"]).max_size(2_000_000),  // Uuid column
Field::column(post::Column::Gallery).media_list(10),                                   // JSON array of ids
FileUpload::make("cover"),

On every write (hooks included, checked after them, and on restore) each id must exist, not be trashed, be visible to the user (media.view and scope), and match accept / max_size; the rows are locked (shared) meanwhile. Media trashed later shows as unavailable in records that reference it.

Media and rich text columns may not declare a default on the entity (any default_value, checked when the panel starts). A default written in a migration is stored without these checks: do not give these columns one.

Rich text

Field::column(post::Column::Content).rich_text(),   // JSON column
RichEditor::make("content"),

Rich text is stored as a document (JSON), not HTML: paragraphs, headings 2–4, lists, quotes, code blocks, rules, line breaks, images (media ids) and the marks bold, italic, strike, code and link (http, https, mailto). Anything else is refused (422); documents are limited to 256 KiB, 10,000 elements, 16 levels and 100 images. Images follow the media rules above (images only).

The panel edits it with TipTap (no injected styles) and shows it with React elements. Headless apps render it with rustcms::admin::rich_text::parse and to_html(&doc, &|id| Some(my_public_url(id))), which escapes all text and attributes.

Limits and operations

  • Referencing media needs media.view_any and media.view (the same check as any relationship). Records a user cannot see are never locked.
  • A write keeps the permissions it started with: revoking media.create while an upload is being received does not stop that upload (the rule for writes in flight).
  • Uploads must finish within an hour: pruning reclaims older unfinished ones, and such an upload then fails with 409 instead of committing.
  • S3: configure an abort incomplete multipart uploads lifecycle rule on the bucket (a cancelled request cannot always abort its upload). The bucket is not probed at boot; the first upload reports a misconfiguration.
  • Local disk: files are synced before their row commits; staged and partial files of interrupted uploads are removed by media:prune after an hour.
  • Downloads are rate limited per user (600 per minute).

Custom fields

When none of the built-in inputs fits, an application can ship its own: a widget written in plain JavaScript, loaded by the panel from an extension script embedded in the application binary.

// The field: any column; the server validates the value by its kind and rules.
Field::column(category::Column::Color).max_length(7),

// The form: the input names its widget, with optional JSON props (≤ 4 KiB).
CustomInput::make("color", "demo/color").props(json!({"palette": [{"value": "#2563eb", "label": "Blue"}]})),

// The provider: scripts (and stylesheets) load in order before the panel renders.
AdminProvider::new()
    .extension_script("demo-color", include_str!("../../resources/admin/js/demo/color.js"))
    .extension_style("demo-color", include_str!("../../resources/admin/css/demo/color.css"))

rustcms make:widget acme/color writes a starting point to resources/admin/js/acme/color.js and prints the registration line.

Widget names are vendor/name (each part 1–32 of a-z, 0-9, -); extension names are 1–64 of the same characters. Each extension is served from {admin}/assets/ext/<name>.<hash>.js|css, with the hash of its content, and cached as immutable.

The widget contract (API version 1)

window.rustcms.registerWidget("acme/color", {
  apiVersion: 1,
  mount(element, ctx) {
    // Build the UI inside `element`; report changes with ctx.onChange(value).
    return {
      update(ctx) { /* the value, disabled or invalid state changed */ },
      unmount() { /* remove listeners; the panel empties `element` */ },
    };
  },
});

ctx holds id (put it on the main control, it is the label’s target), label, value, disabled, invalid, describedBy (ids of the help and error texts, for aria-describedby), props, locale, t(text) and onChange(value). Widgets translate their own text with ctx.t, from catalogs registered while the script loads (window.rustcms.registerTranslations("vi", { None: "Không màu" })); update is called when the language changes (i18n).

  • value is the field’s wire value (a string for decimals and 64-bit integers, an ISO string for dates), null, or undefined when not set. It is a copy: changing it does nothing.
  • onChange(value) is the only way to change the form. undefined means “not set” (the field is left out of the request); null sends null. Calls while disabled, or after unmount, are ignored. mount and update must not call it.
  • update is called only when something changed. React’s development mode may mount, unmount and mount again: unmount must undo mount.
  • Register widgets while the script runs: the registry is frozen once all extensions are loaded. A name can be registered once.

Failures

A script that fails to load, or takes more than 10 seconds, is skipped (the error is in the browser console). A widget that throws, returns no {update, unmount}, or reports a number JSON cannot carry exactly (NaN, Infinity, an integer beyond 2^53) is disabled for the rest of the page’s life, in every field that uses it. In both cases its fields are shown read-only (the stored JSON) and never sent; a required one blocks the form with “cannot be edited here: its widget is not available”.

Trust and CSP

Extensions are application code, not user content: they run with the panel’s full privileges (the user’s session, every API call) and before sign-in, and the panel’s CSP does not isolate them from each other. Only ship code you review. The CSP still applies to them: no inline scripts, no style attributes or <style> elements (use extension_style), images only from the panel or data: URLs.

Pages, slots and cells

The same extension scripts may draw custom pages (registerPage), content beside records (registerSlot) and table cells (registerCell), with the same lifecycle (mount, update, unmount): see Customizing the panel.

In a debug build with APP_ENV=local (cargo run -- serve on your machine), the file is read again at each request: save it and reload the page, no rebuild. A file read this way is checked as at boot; an error answers 500 and is logged (fix the file and reload). If the file is missing, the embedded copy is used. lang:missing reads the copy embedded at build time. PageView::Template("…") takes the text directly and is never read again.

Admin routes

Resources cover database rows. When a panel page drives something else (a service, a process, a remote API), its script needs JSON endpoints of its own. AdminRoutes declares them on the panel’s session, each with the access it requires, checked before the handler reads anything.

// src/routes/admin.rs
use rustcms::prelude::*;

pub fn routes() -> AdminRoutes {
    AdminRoutes::new("/docker")
        .get("/containers", AdminAccess::can("docker.view"), controllers::docker::index)
        .post("/containers/{id}/restart", AdminAccess::can("docker.manage"), controllers::docker::restart)
        .get("/me", AdminAccess::authenticated(), controllers::docker::me)
}

// src/bootstrap/mod.rs
let admin = crate::routes::admin::routes();
app.provider(AuthProvider::new().admin_permissions(&admin));   // docker.view, docker.manage (admin guard)
admin.register(&mut app);

The routes are served under {admin_path}/api/x: /admin/api/x/docker/containers. Nothing built in uses api/x, so an application route never shadows the panel’s own.

Access

AccessWho
AdminAccess::authenticated()any signed-in, active user of the panel
AdminAccess::can("docker.manage")a signed-in user holding that permission in the admin guard (super_admin passes)

There is no public access: an admin route always needs a signed-in user.

  • Access is checked before any extractor reads the path, query or body. A refused request is never parsed: 401 without a session, 403 without the permission.
  • The panel’s guard applies first, as for every admin request:
    • POST, PUT, PATCH and DELETE need an allowed Origin and the session’s CSRF token in X-CSRF-Token (otherwise 403 csrf_mismatch);
    • a disabled user, or a session whose credentials changed (password, sign-out everywhere), is signed out (401);
    • responses are private, no-store.
  • API tokens and JWTs are not admin credentials (401). For token clients, use ApiRoutes.
  • HEAD follows GET; other undeclared methods are 405.

The route’s access gates the route, not the target. Decisions about one record (this container, that site) stay in the handler, after it.

admin_permissions declares each permission in the admin guard (group: the first segment, docker). rustcms permission:sync then creates them, and they appear on the Roles page. register also lists the routes in rustcms route:list, and refuses a method and path declared twice.

Calling them from a script page

A script page runs on the panel’s origin with the user’s session cookie. Fetch the CSRF token once and send it on writes:

const base = document.baseURI.replace(/\/$/, "");   // the panel's <base>, e.g. https://example.com/admin
async function csrf() {
  const response = await fetch(`${base}/api/auth/csrf`, { credentials: "same-origin" });
  return (await response.json()).csrfToken;
}

window.rustcms.registerPage("docker/containers", {
  apiVersion: 1,
  mount(element, ctx) {
    const restart = async (id) => {
      const response = await fetch(`${base}/api/x/docker/containers/${encodeURIComponent(id)}/restart`, {
        method: "POST",
        credentials: "same-origin",
        headers: { "Content-Type": "application/json", "X-CSRF-Token": await csrf() },
        body: JSON.stringify({ force: false }),
      });
      if (response.status === 401) ctx.reload();   // signed out meanwhile
      return response.json();
    };
    // … build the list from ctx.data, wire buttons to restart(id) …
    return { update() {}, unmount: () => element.replaceChildren() };
  },
});

Realtime

A panel page can show live data (stats, logs, progress) through server-sent events, and talk both ways (terminals, consoles) through a WebSocket, from an admin route. The stream runs on the panel’s session, is rechecked while open, and ends when the user signs out or loses access. Changes still go through ordinary POST admin routes.

// src/routes/admin.rs
AdminRoutes::new("/docker")
    .events("/containers/{id}/stats", AdminAccess::can("docker.view"), controllers::docker::stats)
    .post("/containers/{id}/restart", AdminAccess::can("docker.manage"), controllers::docker::restart)
// src/http/controllers/docker.rs
use rustcms::auth::{EventStream, LiveSession};
use rustcms::realtime::{Event, StreamExt, stream, time};

pub async fn stats(live: LiveSession, Path(id): Path<String>, Inject(docker): Inject<Docker>) -> AppResult<EventStream> {
    let source = docker.clone();
    let target = id.clone();
    let events = stream::unfold((), move |()| {
        let (source, id) = (source.clone(), id.clone());
        async move {
            time::sleep(std::time::Duration::from_secs(2)).await;
            let stats = source.stats(&id).await.ok()?;          // ends the stream on an error
            Some((Event::json("stats", &stats).ok()?, ()))
        }
    });
    Ok(live.stream(events).target(move |principal| {
        let (docker, id) = (docker.clone(), target.clone());
        async move { docker.authorize(&principal, &id).await }   // may this user still see it?
    }))
}

  • The route admits the request before the handler runs: the origin, the open limits and the stream’s place. The handler takes LiveSession (the admitted stream, with live.principal()); a handler without it is admitted all the same.

  • live.stream(events) takes any Stream<Item = Event>. Event::json(name, &value) serializes a value (names [a-z0-9_.-], at most 64 KiB of JSON).

  • .target(check) is the per-target authorization. It runs before the first event and at every recheck; Err(Forbidden) or Err(NotFound) ends the stream. The route’s AdminAccess gates the route, while target decides for this container, site or record.

  • A check written once for several streams returns a TargetFuture (a boxed future):

    use rustcms::auth::TargetFuture;

fn sees_container(docker: Docker, id: String) -> impl Fn(Principal) -> TargetFuture + Send + Sync + 'static {
    move |principal| {
        let (docker, id) = (docker.clone(), id.clone());
        Box::pin(async move { docker.authorize(&principal, &id).await })
    }
}
// live.stream(events).target(sees_container(docker, id))

  • A stream must not change anything. Use a POST route for that.

  • rustcms::realtime re-exports what producers need: stream (unfold, once, iter), StreamExt (.chain, .map) and time (sleep, interval).

Many viewers, one producer: the hub

// bound once, e.g. in a provider's register: app.bind(Stats(Hub::new(app.shutdown(), HubLimits::default())))
pub struct Stats(pub Hub<String>);

let subscription = stats.0

    .map_err(|_| AppError::TooManyRequests { retry_after: 5 })?;
Ok(live.stream(subscription.into_events()).target(/* … */))
  • The first subscriber of a key starts its producer; the others share it. The producer stops 5 s after the last one leaves (HubLimits::idle_grace).
  • hub.publish(&key, event) sends to current subscribers, for example after a POST changed something.
  • A viewer that falls behind gets event: resync: reload what the page shows. A producer whose own source lost events (an upstream broadcast that lagged, a reconnect to the source) yields Event::resync(), so pages handle both the same way.
  • The hub knows no users. A key must hold everything that decides its data (container:<id>). Never share a key between users who should see different data.
  • The hub lives in one process: each instance runs its own producers.

ctx.realtime.events(path, handlers) opens the route under {admin}/api/x and returns { close() }.

  • It is closed for you when the view is unmounted or the session changes (sign-in, sign-out, credentials rotated in any tab).
  • It reconnects with backoff after a dropped connection or a server restart.
  • It stops for good on 401, 403 or 404, and when the server ends it with signed_out or forbidden.
  • It is built on fetch. Do not use EventSource: it hides statuses and reconnects on its own after a sign-out.

What the server enforces
Originan Origin, when sent, must be the panel’s; Sec-Fetch-Site, when sent, same-origin; with neither (an old browser), a same-origin Referer. No CSRF token is needed
Accessthe route’s AdminAccess before anything runs (401, 403); HEAD is 405
While openevery revalidate_secs (30): the session, the user and its credential version, its permissions and target. Delivery stops within revalidate_secs + 5 s of a sign-out, a password change, a disabled account or a lost permission (event: closed)
Limitsper instance: max_connections (1000), max_per_user (10), 429 beyond. Opens per user (60/min) and per IP (300/min) use the rate limiter, so with Redis they count across instances
Slow clientsa bounded queue (64 events, 1 MiB): a client that stops reading is dropped (lagging) and never holds the server
Shutdownnew streams get 503; open ones end with closed: shutdown within shutdown_grace_secs (5)

Events end with event: closed and data {"reason": …}: one of signed_out, forbidden, shutdown, lagging or error.

Each recheck reads the session, the user and the grants (about 3 queries), plus what target does. At 1000 streams every 30 s that is about 100 queries per second: raise revalidate_secs or the database pool (database.max_connections) accordingly.

Streams are not cached, carry the session’s Set-Cookie like any admin response, and never renew the session by themselves.

WebSocket

// src/routes/admin.rs
AdminRoutes::new("/docker")
    .socket("/containers/{id}/exec", AdminAccess::can("docker.exec"), controllers::docker::exec)
// src/http/controllers/docker.rs
use rustcms::auth::{LiveSocket, SocketMessage, SocketResponse};

pub async fn exec(live: LiveSocket, Path(id): Path<String>, Inject(docker): Inject<Docker>) -> SocketResponse {
    let target = (docker.clone(), id.clone());
    live.accept(move |mut socket| async move {
        // Dropped when the socket ends: the process goes with it.
        let Ok(mut shell) = docker.exec(&id).kill_on_drop(true).spawn() else { return };
        loop {
            tokio::select! {
                input = socket.recv() => match input {
                    Some(SocketMessage::Text(command)) if command.starts_with("resize ") => {
                        // A command: authorized when it runs, on a fresh principal.
                        let Ok(principal) = socket.authorize().await else { break };
                        if !principal.can("docker.exec") { break }
                        shell.resize(&command[7..]);
                    }
                    Some(SocketMessage::Binary(keys)) => shell.write(&keys).await,
                    Some(_) => {}
                    None => break,
                },
                output = shell.read() => match output {
                    Some(bytes) => if socket.send(SocketMessage::Binary(bytes)).await.is_err() { break },
                    None => break,
                },
            }
        }
    })
    .target(move |principal| {
        let (docker, id) = target.clone();
        async move { docker.authorize(&principal, &id).await }
    })
}

  • The route admits the handshake before the handler runs:

    • a mandatory Origin that is exactly the panel’s (no Referer fallback);
    • the session’s CSRF token in Sec-WebSocket-Protocol (rustcms.v1, rustcms.csrf.<token>, which ctx.realtime.socket sends);
    • the open limits and a place, shared with streams.

    The 101 selects rustcms.v1 only.

  • live.accept(session) runs session once the connection is upgraded and the first check passed (the session, the user, the access, target). session gets an AdminSocket:

    • recv() gives Text or Binary messages, and None once the socket ended;
    • send(message) waits at most send_timeout_secs for a slow client (then the socket ends as lagging) and refuses a message over max_message_bytes (SendError::TooLarge);
    • authorize() checks again now and returns the fresh principal.

  • Authorize every command when it runs: call authorize() and check the command’s own permission on what it returns, never on live.principal(). A raw terminal is one capability: target decides who may use it. Its input is accepted until the next recheck notices a revocation; it cannot check each shell command, nor undo one that ran.

  • Cleanup belongs in Drop. When the socket ends (the client left, a recheck failed, a slow client, the server stopping), the session’s future is dropped at once, before the close frame is sent. A child process needs kill_on_drop. A remote process (docker exec through the API) may need an explicit stop: dropping its stream does not end it.

  • Close codes: 4401 signed_out, 4403 forbidden, 1001 shutdown, 4008 lagging, 1009 too_big, 1011 error (also a session that panics), 1000 when the session returned. Delivering the code is best effort: a connection with unread input may be reset first.

Languages (i18n)

The admin panel speaks English and Vietnamese (en, vi). Only the interface is translated: the content you manage stays in the language it was written in.

Which language a user sees

  1. The language the user chose on their account page (users.locale), if the deployment still offers it;
  2. else the browser’s language (Accept-Language), if offered;
  3. else app.locale.

GET /auth/me returns that language and the panel switches to it. The panel then sends the language it shows (X-Rustcms-Locale) with every request, and labels come back in that language, so what a tab caches always matches what it shows (another tab may have just switched).

# config/app.toml
locale = "en"              # default
locales = ["en", "vi"]     # what users may choose; a subset of what the panel ships

The choice is saved with POST {admin}/api/auth/locale {"locale": "vi"} (null: follow the browser). It is not a credential change: sessions and tokens stay valid. Before signing in, the login page offers the same choice, kept in the browser.

Settings

Settings are values your application reads at run time and administrators change in the panel: a site name, whether enrolments are open, an SMTP password. They live in the database (the settings table, created by rustcms migrate), one row per group, and every instance sees a change as soon as it is saved.

Declaring a group

A group has two halves, in two files (rustcms make:settings GeneralSettings writes both and registers the page):

  • the data, src/settings/general_settings.rs: a struct whose fields are the settings (impl Settings); Default gives their values until someone saves the page. Services, jobs and handlers read it.

Reading settings

Anywhere you have the application state:

let general: GeneralSettings = rustcms::settings::get(&state).await?;
if general.enrolments_open { /* … */ }
let password = general.smtp_password.expose(); // Option<&str>

get reads the row (one query) and is correct on every instance at once, with no cache to clear. Inside a transaction, read with rustcms::settings::load::<GeneralSettings, _>(&txn, &state.config().app.key) to see the transaction’s own writes. A group that was never saved reads as its Default; a field added to the struct later reads as its default until saved.

Secrets

A Secret field is stored encrypted (AES-256-GCM, with a key derived from APP_KEY, bound to its group, field and version). It is never sent to the browser: the page shows only whether it is set, with Set a value / Replace, Clear and Undo. Saving other settings keeps it.

Secret serializes as null and prints as Secret(set), so a settings struct can be logged, queued or serialized without leaking it; read the value with .expose(). A secret’s default is always unset (Secret::default()).

If APP_KEY changes, stored secrets can no longer be decrypted: get fails with an error naming the secret, the page marks it Cannot be read, and the group cannot be saved until each such secret is replaced or cleared. Keep APP_KEY stable, and plan to enter secrets again if you rotate it.

Secrets bound to other settings

SettingField::secret("password").kept_while(&["host", "port", "username"]) keeps the saved secret only while those settings keep their values: changing one without giving the secret again clears it, so a password is never used with a server it was not given for.

validate_in(state, ctx, settings) is validate with the application (its configuration and services), for checks that depend on them.

Mail

AdminProvider::mail_settings() adds the Mail page: the SMTP server of MailSettings (host, port, encryption, user name, password, sender, reply-to), checked against [mail]’s policy when saved, the password bound to host, port and user name. Its Send test mail card (POST /admin/api/settings/mail/test {to}) sends a mail now with the saved settings and answers {ok} or {ok: false, code} (smtp_auth, mail_policy, …); it needs settings.mail.update (checked before the body is read), is limited to five a minute per user, and is recorded in the audit log as mail.test_sent with the recipient masked (a***@example.com).

Permissions and history

Each group declares settings.<group>.view and settings.<group>.update (run permission:sync after adding a group). Saving needs both. Permissions are checked again inside the write, so access revoked meanwhile is honoured.

Saves are optimistic: the page sends the version it was loaded at, and a save made by someone else meanwhile is refused (code stale); the page offers to reload. A save that changes nothing creates no version and no entry. Each change records settings.updated in the audit log with the changed values (secrets and .audit_redact() settings as "[redacted]").

API authentication

Everything outside the admin path uses the API guard: requests carry a personal access token, Authorization: Bearer rcms_<id>_<secret>. Tokens are stored hashed, can expire, and carry abilities: a request may do what both the token’s abilities and the user’s API-guard permissions allow (* = all).

The user needs API-guard permissions first (roles of the api guard):

rustcms role:assign --email you@example.com --role super_admin --guard api   # or a role you created (see Roles & permissions)
rustcms token:create --email you@example.com --name deploy --abilities posts.view_any --expires-days 30

Or over HTTP: POST /api/v1/auth/token with {email, password, token_name, abilities, expires_in_days} (rate limited like sign-in); DELETE /api/v1/auth/token revokes the token used; GET /api/v1/auth/me.

JWT sign-ins

Apps that sign users in (mobile, browser) use short access tokens instead (auth.jwt.enabled, on by default):

POST /api/v1/auth/jwt          {email, password, abilities?}   → 201
POST /api/v1/auth/refresh      {refreshToken}                   → 200
POST /api/v1/auth/jwt/logout   {refreshToken}                   → 204

Both sign-in and refresh answer {accessToken, tokenType: "Bearer", expiresIn, refreshToken, refreshExpiresAt, abilities}. Send Authorization: Bearer <accessToken> like an API token; abilities (omitted = *) are fixed for the sign-in and narrow the user’s API permissions.

  • Refresh before expiresIn runs out, with the latest refresh token. Each refresh token works once: a second use ends the sign-in (both tokens stop working). Refresh one request at a time (share one in-flight refresh across tabs); if a refresh response is lost, sign in again.
  • A refresh token lasts refresh_ttl_days (14) without use; a sign-in lasts at most refresh_family_days (30).
  • Password change, sign-out everywhere and disabling the user end every sign-in from the next request (see revocation).

Token lifetimes

Token lifetimes are 1 to 3,650 days (expires_in_days, --expires-days); without one, a token lasts until revoked.

Revocation

Revocation (password change, sign-out everywhere, disabling) applies from the next request. A request already running is not aborted: your endpoints, like admin resource writes, finish with the credentials checked when they started. Account and RBAC changes made through RbacService are the exception: they re-check the credential version under lock and are refused. See Credential revocation.

Building endpoints that use these credentials is covered in Routing.

Failures

A bucket that does not answer fails a control request within s3.timeout_secs (retries included). Data moves under s3.transfer_timeout_secs per request: size it for your largest part (uploads go in 10 MiB parts) or download over the slowest link you accept. http.timeout_secs (408) bounds the whole HTTP request separately; keep it above s3.timeout_secs so a slow bucket shows as a 500, not a 408.

  • Before the response starts (an upload, or opening a download): the client gets 500, and the error’s details (endpoint, key, credentials) go to the log only.
  • While a download streams: the connection is closed before the announced Content-Length is reached, so the client sees an incomplete download, never an error page inside the file.

media:prune stops taking new work after five minutes; the rest waits for the next run.

Files are always served through the application (no presigned URLs), so authorization and safe response headers apply to every byte.

Several instances

One instance needs nothing more. To run several behind a load balancer:

  1. Build with the redis feature and set REDIS_URL ([redis] url): one standalone Redis (Redis Cluster is not supported).
  2. Give every instance the same APP_KEY, DATABASE_URL and redis.prefix; two applications sharing a Redis need different prefixes (default rustcms:<app.name>).
  3. Share uploads: S3 (feature s3), or one volume mounted by every instance.
  4. Run migrate once per deploy, before the new instances start.

What Redis is used for

  • Rate limits (sign-in, Throttle<N>, uploads, …) are counted in Redis for all instances, atomically across the keys of one check. If Redis does not answer, checks fail closed (500).
  • Periodic jobs (pruning sessions, media deletions, idempotency receipts) take a lease, which avoids most duplicate runs. It is best effort: a lease expires (it is not renewed during a long run), and when Redis does not answer the job runs anyway. Every job is safe to run twice, also at the same time.

Permissions need no Redis: a change made on one instance applies on every instance from the next request (the permission cache follows a counter kept in the database).

Without Redis, several instances still work, but each keeps its own rate limits: run one instance unless Redis is configured. Password-hashing and upload concurrency limits are always per instance (each bounds its own CPU and disk).

Realtime events are per instance too. Each instance runs its own hub producers, and the [realtime] connection limits apply to each one. A change on one instance still reaches every open stream within a recheck, because rechecks read the database.

Your own periodic jobs

// In a provider's `boot`: run every minute, on one instance at a time.
let state = state.clone();
tokio::spawn(async move {
    loop {
        rustcms::jobs::exclusive(&state, "invoices-sync", Duration::from_secs(120), || async {
            // the work; must be safe to run twice
        })
        .await;
        tokio::time::sleep(Duration::from_secs(60)).await;
    }
});

jobs::exclusive runs the job unless another instance holds the lease (without Redis it always runs). If Redis does not answer, the job runs anyway, and a lease can expire during a long run: write jobs that are correct when two run at once (claim rows in the database), the lease only saves work.

The request id is the client’s X-Request-Id when it is a plain token (up to 64 of A-Z a-z 0-9 . _ - :, sent once); otherwise RustCMS generates one. It is also returned in the response and written to the logs, so an entry can be matched with a log line.

Guarantees

Data changes are recorded in the transaction of the change: the entry commits with it and disappears with it on rollback. If the entry cannot be written, the change fails too. This covers every write the admin engine makes (create, update, trash, restore, force delete, creates through a relation, actions), uploads, settings, every RbacService method, API tokens issued or revoked, and the console commands make:user, role:assign, token:create and permission:sync.

Sign-ins and sign-outs (session and JWT) are not data changes: they are recorded on their own once the session is saved or the sign-in ended, best effort. A replayed refresh token ends its sign-in first, then records jwt.reuse_detected (once: later replays change nothing). If that write fails it is logged as a warning and the request still succeeds, and a crash at the wrong moment can lose the entry.

Not recorded:

  • what your hooks and actions write beyond the records they were given (another table, other records) — record it yourself, see below;
  • migrations, seeding, and SQL run outside the application.

Retries are safe: a create or action replayed with the same idempotency key records nothing again.

Actions

An action records one action:<name> entry per selected record it processed, with the changes of the record’s declared fields. If the action moved the record to the trash, the entry’s meta is {"result": "trashed"}; if it deleted it, {"result": "deleted"} without the former values (as for a delete).

What is stored, and what is not

Only declared fields are compared. A field’s values are replaced by "[redacted]" (the entry still says it changed) when the field:

  • is marked .audit_redact(),
  • has a readable(...) rule, or is guarded(),
  • is edited with a password input (TextInput::make(..).password()).

The decision depends on the declaration only, never on who is acting. The parent of a record created through a relation (meta.parent) is redacted when its foreign key field is. A primary key cannot be .audit_redact() (boot fails): it names the record in every entry; use an opaque key, or .audit(false). Keys longer than 255 characters (and keys that look like such a shortened form) are stored as their start and a digest.

fn fields() -> Vec<Field> {
    vec![
        Field::column(customer::Column::Name),
        Field::column(customer::Column::TaxId).audit_redact(),
    ]
}

Values are bounded so an entry never makes a valid write fail: a text over 1,000 characters is kept as {truncated, length, sha256}, a rich text document as {document, bytes, sha256}, long lists and deep values are cut. An entry holds at most 64 KiB of changes and meta together (meta at most 16 KiB); beyond, only the names of the changed fields are kept.

RustCMS never stores passwords or their hashes, API tokens, JWTs, refresh tokens, cookies, CSRF tokens or session ids. Event meta is a fixed set of fields per event, never free-form request data.

To skip a resource entirely (a log table of your own, a cache):

fn meta() -> ResourceMeta {
    ResourceMeta::new("Page view").audit(false)
}

Recording your own events

Inside a hook or an action, ctx.audit records an entry in the same transaction, with the same actor and request:

use rustcms::audit::AuditEntry;

Action::<order::Entity>::new("refund", |ctx, txn, orders, _data| {
    Box::pin(async move {
        for order in orders {
            refund_payment(txn, &order).await?;
            ctx.audit(txn, AuditEntry::new("order.refunded", "orders").key(order.id)).await?;
        }
        Ok(())
    })
})

In your own routes, build the context from the signed-in user and the request, and record in your transaction:

use rustcms::audit::{self, AuditActor, AuditContext, AuditEntry, RequestMeta};

async fn close_course(auth: Auth, request: RequestMeta, State(app): State<AppState>) -> AppResult<StatusCode> {
    let txn = rustcms::db::begin_write(app.db()).await?;
    // … the change …
    let context = AuditContext::new(AuditActor::user(&auth.0.principal), request);
    audit::record(&txn, &context, AuditEntry::new("course.closed", "courses").key(42)).await?;
    txn.commit().await?;
    Ok(StatusCode::NO_CONTENT)
}

AuditEntry::changes takes a {field: [old, new]} object (audit::diff builds one from two snapshots) and AuditEntry::meta any serializable struct; both are bounded like the built-in entries. Do not put secrets in them.

Queues

Work that should not hold up a request (sending mail, building an export, calling another service) goes into a job. Jobs are stored in the database (the jobs table, created by rustcms migrate) and run by workers: inside serve, or in their own process with rustcms queue:work. No Redis or other service is needed.

Writing a job

use rustcms::async_trait;
use rustcms::queue::{Job, JobCtx};
use serde::{Deserialize, Serialize};

#[derive(Serialize, Deserialize)]
pub struct SendWelcome {
    pub learner_id: i64,
}

#[async_trait]
impl Job for SendWelcome {
    const KIND: &'static str = "lms.send_welcome";

    async fn handle(self, ctx: JobCtx) -> anyhow::Result<()> {
        let learner = load_learner(ctx.state.db(), self.learner_id).await?;
        send_mail(&learner, ctx.id).await
    }
}

Dispatching

Add a job in the transaction of the change it follows from. It then exists only if the change commits: an enrolment that rolls back sends no welcome mail.

let txn = rustcms::db::begin_write(state.db()).await?;
// … the change …
rustcms::queue::dispatch(&txn, &SendWelcome { learner_id }).await?;
txn.commit().await?;

In a resource hook or an action, ctx.dispatch(txn, &job) does the same and records the user who asked for it (see Audit log):

async fn after_save(ctx: &Ctx, txn: &DatabaseTransaction, enrolment: &enrolment::Model) -> AppResult<()> {
    ctx.dispatch(txn, &SendWelcome { learner_id: enrolment.learner_id }).await?;
    Ok(())
}

queue::dispatch_with(&txn, &job, Some(when), initiated_by) delays a job; queue::enqueue(db, &job) adds one outside any change.

Running

serve runs queue.workers workers (2) beside the HTTP server. To run them elsewhere, set queue.enabled = false (or workers = 0) on the web instances and run rustcms queue:work in another process; queue:work --once runs the jobs ready now and exits (a cron job, a test), deleting old failed jobs and receipts first.

On Ctrl-C or SIGTERM, workers stop taking jobs at once (while the server finishes its requests), let running ones finish for queue.shutdown_secs (30 s), then stop them. A stopped job is given back, and its interrupted attempt with it: it runs again, even if that was its last attempt.

Failures

A run fails when handle returns an error, panics or times out. The job waits for its backoff and runs again, up to max_attempts; then it stays as failed:

rustcms queue:failed          # list failed jobs
rustcms queue:retry <id>      # or --all: run again, attempts start over
rustcms queue:forget <id>     # or --all: delete

Failed jobs are deleted after queue.failed_retention_days (30).

The table keeps a safe message only. Return a queue::Failure to choose it:

return Err(Failure::new("smtp_rejected", "the mail server refused the message").into());

Any other error is kept as “failed (see the logs for job …)”, and its full text goes to the application log only, so a secret in an error message never reaches the table. Do not put secrets in errors anyway: logs are kept too. A Failure is logged by its code only.

When retrying cannot help (a refused address, a missing template), fail at once instead of using the remaining runs:

return Err(Failure::new("smtp_rejected", "the mail server refused the message").permanent().into());

The job is then failed like one that used all its runs (queue:retry still runs it again).

At least once

A job runs at least once: a worker that crashes after the work but before the job is marked done leaves it to run again. Make effects idempotent:

  • database effects: queue::once(&txn, key) records key in the effect’s own transaction and returns false if it was recorded before (also when another run records it at the same time: one waits for the other);

    let txn = rustcms::db::begin_write(ctx.state.db()).await?;
if !rustcms::queue::once(&txn, &format!("welcome:{}", self.learner_id)).await? {
    return Ok(()); // already done
}
// … the change …
txn.commit().await?;

  • other services: send ctx.id (the job id) as their idempotency key.

Jobs of one queue start roughly in the order they became ready, but with several workers they may finish in any order. Give work that must not wait behind slow jobs its own queue and its own workers (queue:work --queue mail).

Changing a job

Deploy workers that know a job before code that dispatches it. A worker that does not know a job’s kind, or sees a newer VERSION, gives it back for another worker (it does not count as an attempt); after queue.unknown_kind_grace_secs (1 hour) the job fails. To read payloads of an older version, implement upgrade:

const VERSION: u32 = 2;

fn upgrade(version: u32, payload: serde_json::Value) -> anyhow::Result<serde_json::Value> {
    match version {
        1 => Ok(serde_json::json!({ "learner_id": payload["user_id"] })),
        _ => anyhow::bail!("unknown version {version}"),
    }
}

The admin panel shows jobs under System → Queue to users with queue.view, and lets those who also hold queue.manage act on them. Both permissions are declared by the admin panel (group queue); grant them through roles.

  • Forget deletes a failed job and its error.
  • Cancel deletes a job waiting to run, in one statement with the workers’ claim condition: if a worker took it first, the cancel answers 409 (running). What earlier attempts committed stays.
  • Each action re-reads the user’s permissions under the RBAC lock, needs both permissions, and is recorded in the audit log (queue.retried, queue.forgotten, queue.cancelled, subject job, with its kind and queue). Permissions and the audit log

A job does not carry the permissions of the user who asked for it. When the work depends on them, load the user and their grants again in handle. Changes a job records in the audit log appear as actor job, on behalf of its initiator, with credential queue:<kind> (ctx.audit_context()).

Several instances

With source = "settings", whoever has settings.mail.update uses the saved SMTP credentials and makes the application connect to the server they name: treat that permission like a system administrator’s. allowed_hosts and allowed_ports bound where mail may go; in production allowed_hosts is required (boot fails otherwise; * says any server is fine). The policy is checked when the configuration is loaded, when the page is saved, and at every send. Changing the host, port or user name without giving the password again clears the saved password: it is never sent to a server it was not given for.

Sending

use rustcms::mail::{self, MailJob, Message};

// Later, with the change (outbox): queued in the same transaction.
mail::send_later(&txn, MailJob {
    to: vec![learner.email.clone()],
    template: "welcome".into(),
    locale: learner_locale,
    data: json!({ "name": learner.name, "course": course.title }),
}).await?;

// Now (in a request or a job of your own).
let rendered = mail::render(&state, "welcome", "vi", &data)?;
mail::send(&state, &Message::rendered([to], rendered)).await?;

send_later queues a mail.send job: up to 8 runs with backoff on temporary failures (smtp_connect, smtp_temporary, smtp_timeout, smtp_tls, smtp_throttled); permanent ones (smtp_rejected, smtp_auth, mail_not_configured, mail_policy, mail_template, …) fail at once, shown on the Queue page; queue:retry runs one again once fixed. Each run has its own Message-ID ({job}.{run}@{host of APP_URL}), so a mail repeated after a run that the server took but did not confirm can be recognized.

No secrets in data. It stays in the jobs table until the job is done (failed jobs for queue.failed_retention_days). A mail carrying a secret (a password reset link) is sent by a job of its own, which makes the secret when it runs and renders and sends the mail itself (mail::render + mail::send).

Delivery is at least once: a mail may be sent twice when a run is cut after the server took it. A job that must not repeat a mail records that it sent it (queue::once) after sending, and checks first.

Templates

A template is three files per language in resources/views/mail/{locale}/: {name}.subject.txt (one line), {name}.txt, and optionally {name}.html.

app.mail_template(rustcms::mail_template!("welcome", "vi", html));
app.mail_template(rustcms::mail_template!("welcome", "en", html));

They are embedded in the binary; in local development (debug build, APP_ENV=local) they are read again from the files at each send. They are minijinja templates with data, app_name, app_url and locale. Text is not escaped; HTML always is, and nothing marks a value safe (no safe, tojson, escape, autoescape, includes or inheritance). Work, recursion, data (64 KiB) and output (256 KiB per part) are bounded. A subject must be one line: a line break, from the template or from data, fails the mail (mail_template), so no header can be injected. The template of the locale asked for is used, else the one of app.locale.

Errors

Errors are codes (rustcms::mail::MailError); the server’s reply, the addresses, the password and the body never reach a log, a job’s error or a response. See Error codes.

Running the queue

Mails, exports, imports, invitations and your own jobs run on the database queue (Queues).

Where workers run

  • serve runs queue.workers (2) workers next to the web server. Set queue.enabled = false on web instances that should not run jobs.
  • rustcms queue:work [--queue mail] [--workers 4] runs workers alone (a separate process or container). Ctrl-C / SIGTERM lets running jobs finish within queue.shutdown_secs.
  • Run at least one worker somewhere: without one, nothing is mailed, exported or imported (requests still answer, the jobs wait).

Failed jobs

A job fails after its last attempt, at once on a permanent failure (a mail the server refused, a template error), or when no worker knows its kind for queue.unknown_kind_grace_secs. Look at them on System → Queue or:

rustcms queue:failed          # kind, attempts, the safe error code
rustcms queue:retry <id>      # or --all: run again (attempts start over)
rustcms queue:forget <id>     # or --all: delete

Fix the cause first (the SMTP server, the template, a missing permission), then retry. Failed jobs are deleted after queue.failed_retention_days (30).

Deploying

Workers must know a job before code dispatches it: deploy workers first (or together). A job of an unknown kind is given back to other workers, and fails only after queue.unknown_kind_grace_secs (1 hour) — long enough for a rolling deploy.

Delivery

Jobs run at least once: a run cut after its work but before the queue records it runs again. Built-in jobs are written for it (import rows have receipts, export objects are unique per run, mails carry their run’s Message-ID); write yours with queue::once or idempotency keys.

Keep the clocks of every instance synchronized (NTP).

Backup and restore

A backup is three things, taken at the same point in time:

  1. The database (pg_dump, mysqldump --single-transaction, or the SQLite file with sqlite3 database.sqlite ".backup backup.sqlite").
  2. The storage (the storage.root folder, or the bucket: turn on bucket versioning so a snapshot can be read as of a time).
  3. APP_KEY, kept apart from both: without it, saved secrets (the SMTP password) cannot be decrypted, sessions and links stop working.

Taking a consistent backup

Files referenced by the database may be deleted while a live backup runs (pruning, media removal). Either:

  • stop the web and worker processes, dump the database, copy the storage, start again; or
  • dump the database, and restore the storage as of the dump’s time from the bucket’s versions (versioning keeps deleted objects for a while).

Restoring

  1. Stop every web and worker process.

  2. Restore the database and the storage of the same point in time, with the same APP_KEY.

  3. Before opening, end what the backup brought back: every session and JWT sign-in (a sign-in revoked after the backup would work again), links of resets and invitations, and jobs that were waiting:

    DELETE FROM sessions;
DELETE FROM jwt_refresh_tokens;
DELETE FROM jwt_families;
DELETE FROM user_tokens;
DELETE FROM jobs WHERE kind IN ('auth.password_reset', 'auth.invitation', 'mail.send');

    (Revoke API tokens too if the backup may hold some that were revoked since.)

  4. rustcms migrate:status, then rustcms migrate if the code is newer.

  5. Start the processes; users sign in again.

Rehearse a restore on a copy: check that files open and that sign-in works.

Rotating APP_KEY

APP_KEY keys session ids, JWT signatures and refresh tokens, the links of password resets and invitations, and encrypts the secrets of the settings. Rotate it when it may have leaked.

What a new key does:

ItemAfter rotation
Admin sessionsended (everyone signs in again)
JWT access and refresh tokensended
Reset and invitation linksdead (ask for new ones; send invitations again)
Secret settings (SMTP password, API keys)cannot be decrypted: shown as Cannot be read, must be set again
Personal API tokens (rcms_…)kept (not keyed by APP_KEY): revoke them if they may have leaked too

Steps

  1. Note every secret setting you will need to enter again.
  2. rustcms key:generate --show and put the new key in the environment of every web and worker process (an old process keeps the old key in memory).
  3. Stop every process, then start them all with the new key.
  4. Enter the secret settings again (Settings → Mail …) and send a test mail.
  5. Revoke API tokens if needed: each user’s Sign out other sessions (Account page) revokes theirs; or set revoked_at on the rows of personal_access_tokens.

Old backups still open with the old key: keep or destroy them accordingly.

Running mail

See Mail for the configuration.

  • Check it: Settings → Mail → Send test mail sends now with the saved settings and shows the error code (smtp_auth, smtp_tls, mail_policy…).
  • The server is down: mails wait in the queue and are retried with backoff, then fail: mail.send and invitations 8 runs (about 20 minutes of waits), password resets 5 runs (about 2½ minutes; the user asks again). Sending time and a busy queue add to these. Once it is back, rustcms queue:retry --all (or retry the mail.send jobs on the Queue page).
  • A refused message, a bad template: fails at once (not retried). Fix, then retry.
  • The password cannot be decrypted (mail_settings_unreadable, after APP_KEY changed): enter it again.
  • Reset links: a link works auth.password_reset_minutes (60) and once; a request waits at most 15 minutes in the queue. Users ask again from the sign-in page.
  • Invitations: links work auth.invitation_days (7); Send the invitation again on the user page makes a new one (the old one stops working).
  • Several instances: mail.max_per_minute counts per process.
  • Development: Mailpit (docker compose up mailpit, http://localhost:58025) catches every mail; or the log driver with RUSTCMS_MAIL__LOG_BODY=true (local only) prints them.

Seats

A course takes at most capacity active enrollments, and a learner enrolls in a course once (withdrawing and coming back change the same row). The rules are one function in the service:

// src/services/enrollment_service.rs
pub async fn check(txn, course_id, learner_id, status, current) -> AppResult<Result<(), Refusal>>
// AlreadyEnrolled (said before the seats), NoSeat, NoCourse, UnknownStatus

It counts the course’s enrollments, so it runs under the course’s row lock:

  • in the panel, the enrollment resource declares .lock_parent("course_id", "courses"): every enrollment write locks its course first (both courses when it moves), then the hooks call check (parent locks);
  • the course’s Enroll a learner… action (staff: enrollments.create) asks for a learner in a dialog; the action locks the course, then calls enrollment_service::enroll_in(txn, …) in its transaction. A refusal (already enrolled, no seat) answers 422 in the dialog and nothing is kept;
  • elsewhere, enrollment_service::enroll opens its own transaction, locks the course and calls enroll_in. The enrollment seeder uses it, so seeding never overfills a course.

Concurrent requests for the last seat get one 201 and one 422; a course and its enrollments changed at the same time never deadlock (the course is always locked first, the order its deletion cascades in). A capacity below the active enrollments is refused. The unique constraint enrollments_course_learner_key stays as the last line of defense, mapped to a message with ResourceMeta::unique.

To move an enrollment, change its course_id (staff): the seat is checked in the new course. To withdraw, set status to withdrawn; setting it back to active needs a free seat.

Instructors

Staff hold lms.all_courses; everyone else sees what they teach. Each resource’s scope() adds an EXISTS subquery from the model (a join could repeat rows):

// src/admin/resources/lesson_resource.rs
fn scope(query: Select<lesson::Entity>, ctx: &Ctx) -> Select<lesson::Entity> {
    match instructor(ctx) {
        None => query,
        Some(me) => query.filter(course::taught_by(me, (lesson::Entity, lesson::Column::CourseId))),
    }
}

The scope applies to lists, direct ids, options, relations and writes: another teacher’s course, its lessons, enrollments and learners answer 404, are not offered as options, and cannot be picked for a lesson (also not by overriding course_id when creating from a course’s page).

Field rules and the policy do the rest:

  • instructor_id is set only with courses.assign_instructor, and must name a user. Lessons and enrollments lock their course first, so an instructor removed from a course loses access to it at once.
  • progress is never set when enrolling and changes only with enrollments.update_progress. EnrollmentPolicy lets that permission update an enrollment; the other fields stay closed to it. It also refuses abilities before any lookup (admits: 403 whether an enrollment exists or not) and never filters records itself (view_depends_on_record() == false: lists need no scan), since the scope decides visibility.

Settings, job, languages

Database schema

The framework’s migrations (rustcms::migration, run by rustcms migrate before your own) create the tables below. Your models live next to them in the same database. Column types are shown portably:

  • instant: TIMESTAMPTZ on PostgreSQL, DATETIME(6) in UTC on MySQL, text on SQLite;
  • bigint id: auto-increment BIGINT.

Never write the access-control tables yourself: every change to roles, permissions and their assignments goes through RbacService (Roles & permissions), which checks the actor, locks, audits and invalidates the permission cache.

Reading them

For reports or support, read-only SQL is fine. For example, everyone holding a permission in the admin guard:

SELECT DISTINCT u.id, u.email
FROM users u
JOIN model_has_roles mr ON mr.model_type = 'user' AND mr.model_id = CAST(u.id AS CHAR(20))
JOIN roles r ON r.id = mr.role_id AND r.guard_name = 'admin'
LEFT JOIN role_has_permissions rp ON rp.role_id = r.id
LEFT JOIN permissions p ON p.id = rp.permission_id AND p.orphaned = FALSE
WHERE p.name = 'posts.update' OR r.name = 'super_admin';

(Direct grants: the same through model_has_permissions. On PostgreSQL, use CAST(u.id AS TEXT).) Writes go through RbacService or the System pages.

Admin API

The admin panel talks to the server through a JSON API under <admin_path>/api (default /admin/api). You rarely call it yourself, but it is what resources expose, and its rules are the rules of every client: tests, scripts, a custom front end.

Every request uses the admin session (cookie) and, for writes, the CSRF token and an allowed Origin (Authentication). Responses, errors included, are Cache-Control: private, no-store; unknown paths under /api are JSON 404. Errors follow the standard format; values follow the wire format.

Lists

page, per_page (≤ 100), sort (title or -title), search (case-insensitive as the database folds case: Unicode on PostgreSQL, ASCII on SQLite; % and _ are literal), and filters filter[<field>][<op>]=<value> with op in eq, in, gt, gte, lt, lte. Values are read by field type: filter[published][eq]=true, filter[category_id][in]=1,2. JSON clients use the strict wire format.

trashed=with|only lists trashed records too, or only them, on resources with soft deletes (table.softDeletes); elsewhere it is a 422. It needs the restore or force_delete ability (schema abilities.restore / abilities.forceDelete), otherwise 403, and a trashed record is listed only if the policy allows view and restore or force_delete on it.

Records

{
  "key": "0199d3a4-…",
  "title": "Hello",
  "abilities": { "delete": true, "update": true, "view": true },
  "data": { "title": "Hello", "author_id": "7", "price": "10.50", "category_id": 1 },
  "labels": { "category_id": "News" }
}
  • data holds readable fields only, and is empty (no title, no labels) when the user may not view the record, e.g. the result of an update-only write.
  • abilities also holds one entry per action ("publish": true).
  • labels holds titles of related records. A related record the user may not see is shown as #<key>.
  • trashed: true marks a record in the trash (soft deletes; absent otherwise). Its abilities are view, restore and force_delete only; an active record of a soft-delete resource has restore and force_delete false.

Retrying writes safely

POST …/records (create) and POST …/actions/{action} accept an Idempotency-Key header (1–128 of A-Z a-z 0-9 _ -, otherwise 422 on idempotency_key). The key is claimed in the write’s transaction, so the write and its receipt commit together or not at all. Repeating the request with the same key, by the same user, within 24 hours:

  • same request (body compared canonically: key order does not matter) → the first result, not applied again: a create answers its record as the user may see it now (key only when no longer visible); an action answers the first run’s outcome with "replayed": true. Admission is checked again (403 if the user lost the ability). Action outcomes, first or replayed, list processed and denied keys only for records the user may view now;
  • different request → 422 on idempotency_key;
  • the first request still running → the retry waits (up to 5 s), then answers 409 write_conflict (nothing applied; retry later).

Keys are per user, resource and operation. At most 1,000 live keys per user (429 beyond). idempotency:prune deletes expired receipts (serve does it hourly). Updates and deletes take no key: repeating them converges.

Limitations

What RustCMS does not do yet, and behaviours to know before relying on it.

Not supported yet

  • Choosing belongs-to-many links in the record’s own form (use the relation manager on its page); belongs-to-many to the same resource, two relations over one pivot table, or to a resource declaring lock_parent.
  • Excel files; dashboard widgets other than counts (no sums or averages), charts in time zones other than UTC.
  • Email verification flows (invitations mark the address verified).
  • Mail rate limits shared between instances (max_per_minute counts per process); DKIM signing; attachments.
  • Settings of kinds other than text, integer (i32), boolean, select, key/value, date and secret (store larger numbers or decimals as text).
  • Translations of content (only the interface is translated: English, Vietnamese).
  • Composite primary keys; sorting by related columns.
  • Image resizing and thumbnails, range requests, public media URLs (add your own route).
  • MariaDB; Redis Cluster.
  • Idempotency keys outside resource creates, actions and media uploads.
  • Managing API-guard roles from the panel (use rustcms role:assign).

Writes in flight

Signing out one session, or revoking one API token, does not abort a change that the same credential already started. Sign-out everywhere, password changes and disabling a user apply from the next request, and changes made through RbacService re-check the credential under lock. A resource write keeps the permissions it started with.

Databases

  • SQLite decimals are stored as REAL: values are shown at the column scale, but precision is that of a 64-bit float. Use PostgreSQL or MySQL for money.
  • Search compares LOWER(column) LIKE LOWER(pattern): case-insensitive for all of Unicode on PostgreSQL, for ASCII only on SQLite. It uses no index; full-text search is out of scope.
  • MySQL specifics (collation, non-transactional DDL) are in Database.

Deployments

One instance, or several sharing one standalone Redis and shared media storage (Several instances). Password-hashing and upload concurrency limits are per instance.

Size

A release binary with the panel and the three database drivers is about 29 MB (23 MB stripped); the panel’s JavaScript is about 0.55 MB (175 KB gzipped).
